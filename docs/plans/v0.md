# V0 Evidence-Gated Implementation Plan

**Status:** Approved sequence
**Planning principle:** Move quickly toward validated learning, not an arbitrary date.

## Gate 0 — Durable knowledge

### Work

- Create the approved repository knowledge base.
- Self-review for contradiction, duplication, and semantic-boundary loss.
- Obtain one independent read-only architecture/documentation review.
- Fix accepted findings and commit documentation before implementation.

### Exit evidence

Future agents can understand the mission, boundaries, V0, evals, unknowns, and sequence without this planning conversation.

## Gate 1 — Runnable foundation and visible product hypothesis

### Initial implementation baseline

- Modular monolith using the current stable Next.js App Router and strict TypeScript
- Node 22 and pnpm 11
- Tailwind CSS plus small accessible UI primitives where needed
- Zod validation
- Supabase-hosted PostgreSQL with Drizzle and explicit migrations
- OpenAI Responses API; GPT-5.6 Terra at low reasoning is an initial configurable experiment, not a permanent per-stage choice
- Provider-neutral search adapter; provider remains unresolved until R-01
- Vitest, Testing Library, and Playwright
- Vercel as the initial protected-hosting target

Exact dependency versions are locked by the scaffold task and updated deliberately. Model, reasoning, provider, and visual choices remain evidence-driven.

### Work

- **V0-01:** Scaffold the modular Next.js/TypeScript application, quality commands, deterministic tests, browser smoke test, and service-scoped environment validation. Scaffold, tests, and fixture UI run without external credentials; only a live adapter or deployment fails clearly when its own required secret is missing.
- **V0-02:** Build a polished fixture-driven landing/task/results shell and inspect desktop/mobile screenshots.
- **PRE-01 in parallel:** Verify OpenAI, SERP trial, Supabase, and protected-hosting access; set spending limits and keep secrets outside Git.
- **R-01 in parallel after scaffold:** Run the timeboxed provider comparison and record a provisional decision.

PRE-01 does not block scaffold or fixture UI. Only a task that calls a service depends on that service's successful preflight.

### Exit evidence

The application runs, automated checks work, and the intended shopping hierarchy can be judged in a real browser before backend intelligence is built.

## Gate 2 — Prove the semantic engine

### Work

- Persist independently identified tasks, task revisions, messages, task-local concepts, criteria, and reactions.
- Implement the typed value grammar and explicit authority/source/strength/lifecycle dimensions.
- Implement deterministic state patches, superseding, removal, indifference, idempotency, undo, and brief projection.
- Build timeout/error/state-preservation handling for any external component introduced.

### Exit evidence

Golden state tests prove that flexible budget remains flexible, preference does not become constraint, unknown remains absent, change of mind removes conflicting active truth, scope cannot leak, and multiple tasks do not become a singleton.

## Gate 3 — Prove AI context acquisition

### Work

- Add the structured user-message → proposed-patch contract.
- Add qualitative ASK / SEARCH / SHOW-REFINE selection.
- Keep question impact/effort qualitative and present one question at a time with no total count.
- Trace actual downstream information gain.
- Handle malformed output, timeout, retry, and stale revision in this slice.

### Exit evidence

Cap, shelving, headphones, and exact-lookup fixtures produce acceptable state and question decisions without semantic leakage or questionnaire behaviour.

## Gate 4 — Prove retrieval

### Work

- Finalise the provisional provider choice from live evidence.
- Implement provider-neutral search and normalisation contracts.
- Generate task-revision-bound hypotheses and purpose-labelled queries.
- Run literal versus expanded queries; retain query/candidate lineage.
- Handle concurrent calls, partial results, provider errors, and factual fallback.

### Exit evidence

Retrieval reports show which useful candidates each query/provider found, where targets were lost, and whether expansion improves recall. Poor retrieval is distinguishable from poor judgement.

## Gate 5 — Prove product understanding

### Work

- Create task/run-contextual observations from actual SERP evidence and optional images.
- Create criterion assessments with coarse status plus qualitative relation/evidence.
- Produce evidence-grounded comparative groups without scores.
- Test observation independently of assessment/judgement.
- Measure actual evidence gaps before deciding on selective page inspection.

### Exit evidence

The system avoids unsupported suitability claims, preserves unknowns, distinguishes observation from assessment, and identifies whether deeper evidence materially improves the golden cases.

## Gate 6 — Complete the first vertical shopping loop

### Work

- Integrate real results into the consumer shell.
- Add Save, Not for me, undo, retailer link-out, and persisted reruns.
- Process rejection explanations through the normal message/state contract.
- Make refinement update state visibly, mark old judgement stale, and rerun search.
- Test partial failures and refresh reconstruction in each feature.

### Exit evidence

A shopper can complete natural request → brief → ask/search → real results → save/reject → refine → persisted rerun, and failures can be assigned to a system layer.

## Gate 7 — Decision UX and external learning

### Work

- Add lightweight comparison of two or three saved products.
- Improve evidence presentation, market-aware questions, product investigation, and closing decision support.
- Iterate visual hierarchy through screenshots and real use; no palette is permanent.
- Protect paid endpoints and add invited-user identity/privacy only before external testers.

### Exit evidence

The product reduces retailer-tab comparison work and can be used safely by a small external test group.

## Deferred

- Long-term/workspace context
- Cross-task product knowledge
- Broad entity resolution
- Multiple markets/search engines
- Affiliate monetisation
- Room visualisation
- Broad crawling
- Fine-tuning, vector database, microservices, queues

## Next bounded tasks after this document is committed

1. V0-01 scaffold and quality gate.
2. PRE-01 external service preflight in parallel.
3. V0-02 fixture-driven consumer shell.
4. R-01 timeboxed provider comparison in parallel once the scaffold can store fixtures/tests.

Do not reopen the whole architecture for ordinary implementation choices. Stop at an evidence gate when a protected invariant fails or an unknown materially changes the next step.
