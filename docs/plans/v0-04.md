# V0-04 — Deterministic state transitions and brief projection

## Status and objective

This is the execution plan for the second Gate 2 code slice. V0-04 will prove
that already-structured, validated shopper truth can change deterministically,
atomically, and idempotently without an LLM. It owns authoritative patch
application, optimistic revision protection, criterion lifecycle transitions,
forward-history undo, deterministic applied deltas, and brief projection.

This plan does **not** authorize implementation. Implementation starts only
after independent review accepts the expensive transition, receipt, CAS, undo,
and projection decisions below.

V0-04 accepts structured commands created directly by tests or trusted
application code. V0-05 will later interpret natural-language inputs into patch
proposals and handle stale-proposal reinterpretation. V0-04 rejects stale input;
it never interprets, repairs, or semantically completes a proposal.

## Exact boundary

### In V0-04

- A versioned, strict deterministic patch grammar.
- Ordered multi-operation patches with bounded local concept references.
- Exact operations for concept creation, criterion addition, replacement,
  relaxation, tightening, removal, indifference, and no change.
- Server-owned task scope, identities, authority, provenance, lifecycle,
  timestamps, and revision assignment.
- One atomic PostgreSQL transaction for each meaningful applied patch or undo.
- Task-row locking plus a conditional revision compare-and-swap.
- Durable patch idempotency and exact retry results through one minimal
  application-receipt table.
- Forward-only, latest-applicable-change undo.
- A deterministic, presentation-neutral applied state delta.
- A rebuildable structured brief plus deterministic shopper-language formatting.
- Pure unit tests and real PostgreSQL lifecycle, rollback, idempotency, and
  concurrency tests.

### Not in V0-04

- OpenAI/model calls, prompts, natural-language interpretation, clarification
  policy, or ASK / SEARCH / SHOW decisions.
- Automatic stale reinterpretation.
- Search hypotheses, retrieval, providers, candidates, products, reactions,
  observations, assessments, ranking, or judgement.
- Comparison persistence before real task-scoped `CandidateListing` identity.
- Authentication, workspace/global preferences, memory, trace infrastructure,
  event sourcing, or a generic audit framework.
- UI integration or replacement of the accepted V0-02 fixture shell.
- Category-specific schemas, synonym matching, or semantic concept
  deduplication.

## Existing V0-03 foundation consumed

The plan composes with the merged code at
`c6648e93d0d61dabaaec865543988fbc8a86e0a4`; it does not assume a different
persistence layer.

- `ShoppingTask.currentRevision` is a non-negative `bigint`, starts at zero,
  and is not mutated by any existing production adapter.
- `TaskInput` is a task-scoped idempotent source snapshot with a frozen request
  fingerprint and the revision seen by the client. It is provenance, not an
  applied state event.
- Exact message/input identity is relationally protected, and retry reads fail
  closed if message task, input, or revision diverges.
- `ConceptDefinition` is task-local, open-ended, typed by a small value-family
  grammar, and written only through a caller-owned transaction.
- `DecisionCriterion` versions have independent authority, strength, target,
  typed value, lifecycle, revision, and lineage fields.
- A partial unique index permits at most one active row per task/lineage.
- A deferred composite successor foreign key keeps a superseding row in the
  same task, lineage, and concept.
- Existing criterion writes canonicalise measurements, reject comparison
  persistence, require valid source roles, and run only in a caller transaction.
- Reads parse durable JSON and provenance and fail closed on corrupted or
  non-canonical state.
- Existing writes reject a row revision above the currently stored task
  revision. V0-04 must therefore advance the task row inside its uncommitted
  transaction before inserting rows at the new revision; rollback still makes
  the externally visible change all-or-nothing.

No current table identifies a successful state application or can return its
server-generated result on retry. That is the one schema gap V0-04 must fill.

## Deterministic patch contract

### Application command and proposal are separate

The aggregate service receives a trusted application command around an
untrusted structured proposal:

```ts
type ApplyStatePatchCommandV1 = {
  applicationSchemaVersion: 1;
  applicationKind: "patch";
  taskId: ShoppingTaskId;            // route/service scope, never model output
  expectedRevision: bigint;          // revision of the interpreted snapshot
  source: AuthoritySourcePlanV1;     // trusted application context
  patch: StatePatchProposalV1;       // strict deterministic proposal
};

type StatePatchProposalV1 =
  | {
      schemaVersion: 1;
      outcome: "change";
      operations: readonly PatchOperationV1[]; // 1..32, ordered
    }
  | {
      schemaVersion: 1;
      outcome: "no_change";
    };
```

There is no generic JSON Patch path/value mechanism. Every operation is a
closed, versioned exact object. Unknown keys fail validation.

The command does not accept persisted criterion IDs for new rows, lineage IDs,
task IDs inside new records, created/ended revisions, lifecycle, timestamps,
criterion-source rows, or resulting revision. The server allocates or derives
all of them. References to existing concept or criterion IDs are selectors, not
permission to assign new identities.

### Authority source plan

Authority is not a patch field. Trusted orchestration supplies one of:

```ts
type AuthoritySourcePlanV1 =
  | {
      kind: "user_explicit";
      inputId: TaskInputId;
    }
  | {
      kind: "user_confirmed";
      originInputId: TaskInputId;
      confirmationInputId: TaskInputId;
    };
```

The explicit `inputId`, or the confirmed plan's `confirmationInputId`, is the
causal input and durable application identity. The service validates every
referenced input in the task and resolves an exact `UserMessage` whenever the
input kind is `message`. A confirmed plan requires distinct origin and
confirmation input IDs; one record cannot prove both roles merely because a
caller labels it twice.

For a new criterion:

- `user_explicit` derives authority `user_explicit` and one `origin` source from
  the causal input.
- `user_confirmed` derives authority `user_confirmed`, an `origin` source from
  `originInputId`, and a `confirmation` source from `confirmationInputId`.

For a successor criterion, the same sources describe the new meaning and the
causal input is also stored with role `change`. One input may therefore have
both `confirmation` and `change` roles when it confirmed a change; the roles are
semantically distinct and the existing uniqueness constraint permits them.

For removal, the causal input is attached to the ended criterion with role
`change`. The old origin/confirmation sources remain intact. The proposal never
constructs source roles or chooses authority directly.

V0-04 can prove source identity, task ownership, input kind, exact message
identity, role completeness, and temporal admissibility. It cannot prove that
the shopper's prose entails a proposed semantic value; that is V0-05's evaluated
interpretation responsibility.

### Concept references

```ts
type ConceptRefV1 =
  | { kind: "existing"; conceptId: ConceptDefinitionId }
  | { kind: "created"; localRef: PatchLocalRef };

type CreateConceptOperationV1 = {
  op: "create_concept";
  localRef: PatchLocalRef;
  label: string;
  definition: string;
  valueFamily: ConceptValueFamily;
  canonicalUnit: MeasurementUnit | null;
};
```

`PatchLocalRef` is a bounded stable identifier such as
`concept_budget_primary`; it is not a UUID and is never persisted as entity
identity. The server allocates the final concept UUID. Labels and definitions
have the existing V0-03 bounds and value-family/unit compatibility.

No concept label is unique. Existing concepts are reused only when the proposal
references an exact existing concept ID. V0-04 does not case-fold labels, search
for synonyms, or decide that two definitions mean the same thing.

A `create_concept` operation must be referenced by a later criterion or
indifference operation in the same patch. A concept-only patch is invalid: V0-04
does not persist speculative concepts that create no authoritative semantic
state.

### Exact criterion target

```ts
type ProposedCriterionTargetV1 = {
  strength: CriterionStrength;
  targetSemantics: Exclude<TargetSemantics, "indifferent">;
  semanticValue: Exclude<SemanticValueInput, { kind: "indifferent" }>;
};
```

The complete resulting target is always supplied. `replace_target`, `relax`,
and `tighten` never contain instructions such as “make this looser.” Existing
V0-03 parsers validate value shape, strength, target semantics, market currency,
unit dimension, canonical storage, and the comparison deferment. Indifference
is intentionally unavailable through these ordinary target shapes and can enter
state only through `mark_indifferent`, which applies its fixed null-strength,
indifferent-target/value shape server-side.

### Operations

```ts
type PatchOperationV1 =
  | CreateConceptOperationV1
  | {
      op: "add_criterion";
      concept: ConceptRefV1;
      target: ProposedCriterionTargetV1;
    }
  | {
      op: "replace_target" | "relax" | "tighten";
      targetCriterionId: CriterionId;
      result: ProposedCriterionTargetV1;
    }
  | {
      op: "remove";
      targetCriterionId: CriterionId;
    }
  | {
      op: "mark_indifferent";
      concept: ConceptRefV1;
      replacesCriterionIds: readonly CriterionId[];
    };
```

The target of replace/relax/tighten/remove is the exact active criterion-version
ID. The server derives its lineage and concept. A caller cannot redirect a
successor to another lineage or concept. Expected-revision CAS protects the
snapshot, while the exact version ID makes stale or ambiguous targeting fail
clearly.

`add_criterion` always creates a new server-owned lineage. More than one active
criterion may legitimately use the same concept.

## Operation ordering and local references

- Operations execute in array order and the order is retained by the
  fingerprint and applied delta.
- Local refs are unique within the patch and may only refer backward to an
  earlier `create_concept` operation.
- Only concepts have local refs. New criterion rows cannot be targeted by a
  later operation in the same patch; callers express the intended final target
  in the original add.
- `replacesCriterionIds` is a semantic set and must contain unique IDs in
  lexicographic order. The coordinator rejects rather than silently reorders an
  unstable representation.
- A patch may affect one lineage at most once. The coordinator resolves exact
  targets before writes and rejects duplicate lineage consumption, including a
  target also listed by `mark_indifferent`.
- Multiple added criteria for one concept remain legal and get independent
  lineages.
- Every created concept must be consumed. Duplicate, missing, forward, or unused
  refs are typed invalid-patch-reference failures.
- This is a linear bounded program, not a DAG or workflow engine.

## Operation semantics

### Add criterion

- Resolve an existing or earlier-created concept.
- Allocate criterion and lineage UUIDs server-side.
- Parse the complete target in task/concept context.
- Create one active row at `nextRevision` with derived authority and sources.
- Emit `criterion_added` with the authoritative after snapshot.

The engine does not decide whether another active criterion on the concept is a
semantic conflict. If another known lineage must end, the proposal must target
it explicitly in the same patch.

### Replace target

- Require the exact target row to be active in the task.
- Reject an identical canonical resulting target; that is `no_change`.
- Allocate a new criterion UUID in the same lineage and concept.
- Set the predecessor to `superseded` with
  `endedRevision = nextRevision` and `supersededById = successor.id`.
- Insert the active successor at `createdRevision = nextRevision`.
- Persist new origin/confirmation provenance plus the causal `change` source.
- Emit `criterion_replaced` with before and after snapshots.

Historical meaning is never updated in place.

### Relax and tighten

Persistence is structurally identical to replacement, but the declared intent
is preserved in the delta as `criterion_relaxed` or `criterion_tightened`.
The proposal supplies the exact resulting target; the engine does not calculate
it.

V0-04 adds only a narrow, deterministic contradiction guard:

- comparable strength-only changes use `hard > strong_preference > preference`;
- comparable money ceilings use the integer amount;
- comparable canonical measurement one-sided bounds use exact decimal ordering;
- for categorical values with unchanged strength, operator, and every other
  semantic dimension, `include` may prove relaxation only when the resulting
  set is a superset and tightening only when it is a subset;
- under the same comparability conditions, `exclude` reverses that relation: a
  resulting subset may prove relaxation and a resulting superset may prove
  tightening;
- categorical `prefer` has no universally safe monotonic relax/tighten relation
  from set inclusion alone, so the guard makes no directional claim for it.

If every changed dimension is safely comparable and proves the opposite
direction, reject the declaration. If the change is mixed, qualitative, or not
universally comparable, retain the exact operation intent without pretending to
prove it. This catches “relax maximum £30 to maximum £20” without building a
fuzzy or category-specific comparator. Direction and criterion strength remain
independent; the narrow set proof never promotes a preference into eligibility
or treats an operator change as comparable.

### Remove

- Require the exact target row to be active.
- Set it to `removed`, `endedRevision = nextRevision`, no successor.
- Add exact causal `change` provenance.
- Emit `criterion_removed` with the active before, the same row's durable
  removed after-state, and no active successor.
- Delete nothing and create no unknown-valued replacement.

Removing an indifference criterion returns that concept to unknown/absence when
no other active criterion remains.

### Mark indifferent

Indifference is concept-level remembered truth. It is structurally incompatible
with simultaneous active non-indifferent criteria for that same exact concept.
This is the only additional concept-level conflict rule in V0-04; it follows
from the existing meaning of indifference and does not limit multiple ordinary
criteria per concept.

`replacesCriterionIds` must be the exact set of all active criteria currently on
the referenced concept:

- With no active criteria, the list is empty.
- With active criteria, every one must be named explicitly. V0-04 does not infer
  which truths the shopper intended to discard.
- An already-active indifference should produce `no_change`, not another row.

The operation removes each named active row at `nextRevision`, attaching change
provenance, then creates one new active indifferent criterion in a new
server-owned lineage. A new lineage is necessary because one concept may have
several prior active lineages and a single successor cannot belong to all of
them. The delta preserves every active before, every removed after-state, and
the new indifference row.

Final-state validation guarantees at most one active indifference per concept
and no active ordinary criterion beside it. Moving from indifference to a new
preference therefore requires an explicit remove plus add in one patch.

### No change

`no_change` is a distinct patch variant with no operations.

- It validates source ownership and exact current expected revision.
- It writes a durable idempotency receipt with an empty delta.
- `baseRevision` and `resultingRevision` are equal.
- It does not update `ShoppingTask.currentRevision` or semantic state.
- It returns the current structured brief and revision.

A change patch whose operations collapse to no semantic difference is rejected;
the caller must state `no_change` explicitly.

## Transaction and revision/CAS algorithm

### Pre-transaction work

1. Preserve the original command/proposal wire envelope and validate it with a
   strict, non-transforming structural boundary: exact keys, discriminators,
   primitive types, bounds, and closed operation shapes, but no `.trim()`, case
   folding, Unicode normalization, semantic parsing, or unit conversion.
2. Derive the causal input identity from that structurally accepted envelope and
   calculate the V1 application fingerprint from the preserved raw values.
3. Separately parse the same accepted envelope through the existing V0-03 domain
   contracts to obtain canonical values for compilation and storage. This raw
   boundary is a thin wire-preservation layer, not a second semantic model; the
   existing domain schemas remain the sole semantic validators.
4. Perform pure dependency checks that require no database state.

Malformed input fails before a transaction and writes nothing.

### Transaction algorithm

For a forward patch:

1. Begin one PostgreSQL transaction.
2. Probe for an existing receipt by `(taskId, causalInputId)` before resolving or
   validating any alternate non-causal source input or message. If present,
   fail-closed-validate the persisted receipt and its materialized references,
   compare its frozen fingerprint, and return its prior result on a match or
   throw an idempotency conflict on mismatch. A retry cannot replace committed
   application identity semantics with a newly supplied missing, cross-task, or
   otherwise invalid origin input.
3. If no receipt exists, load every referenced source `TaskInput` for the task
   with `FOR UPDATE` in stable UUID order. The causal row is the
   application-idempotency mutex; stable ordering prevents confirmed-source
   commands from deadlocking when inputs overlap.
4. Recheck the receipt after acquiring the source locks, before resolving exact
   messages or performing full source-plan validation. This closes the
   concurrent first-application race. Handle a found receipt exactly as in step
   2; only an absent receipt proceeds to full source/message validation.
5. Resolve and validate every referenced source input and exact message inside
   the transaction.
6. Lock the `ShoppingTask` row with `FOR UPDATE` and require
   `currentRevision === expectedRevision`. Otherwise throw typed stale revision
   and write no receipt.
7. Require each source input's client-seen revision to be no later than the
   patch's expected revision. Equality is the normal first application. A later
   V0-05 reinterpretation may intentionally build a fresh structured patch at a
   newer revision from an older source; V0-04 does not perform that
   reinterpretation.
8. Load and fail-closed-parse the task-local concepts, active criteria, exact
   target histories, sources, and references required by the patch.
9. Resolve local refs and compile every operation into a server-owned execution
   plan. Allocate IDs, canonicalise values, validate final state, temporal
   lineage rules, comparison deferment, and all operations before any write.
10. For `no_change`, insert the final receipt with equal base/result revisions
   and commit without updating the task.
11. For a meaningful patch, set `nextRevision = expectedRevision + 1` and execute
   the conditional CAS:

   ```sql
   UPDATE shopping_private.shopping_tasks
   SET current_revision = current_revision + 1, updated_at = now()
   WHERE id = :task_id AND current_revision = :expected_revision
   RETURNING current_revision;
   ```

   The task lock serializes writers; the conditional update remains the final
   database assertion. Zero rows is a typed stale/internal-concurrency failure.
12. Apply every compiled concept, criterion, lifecycle, and source write using
    `nextRevision`; then insert the complete application receipt and versioned
    applied delta.
13. Re-read/validate the resulting current state and build the brief in the same
    transaction where practical.
14. Commit. Any failure rolls back the CAS, all earlier operations, sources,
    receipt, and generated IDs together.

The CAS occurs before new-revision child inserts because the accepted V0-03
transactional writers reject child revisions above the task row. It remains
externally atomic: PostgreSQL exposes neither the task update nor child writes
before commit. No external call occurs inside the transaction.

### Concurrency guarantees

- Different sources at revision N serialize on the task row. One commits N+1;
  the other observes N+1 and fails stale before semantic writes.
- The same source serializes on its `TaskInput`. The loser sees the committed
  receipt and returns the same result rather than failing stale.
- A same-source different fingerprint conflicts before alternate non-causal
  source/message validation or state mutation, even when the retry supplies a
  missing or cross-task origin input.
- A later invalid operation aborts the entire transaction, including the CAS and
  any earlier operation writes.

## Durable application idempotency and schema addition

V0-04 should add exactly one table,
`shopping_private.state_change_applications`. It is a mutation receipt, not an
event store and never reconstructs current truth.

| Column | Shape | Reason |
| --- | --- | --- |
| `id` | server UUID primary key | Stable receipt/undo target identity. |
| `task_id` | UUID | Aggregate ownership and composite foreign keys. |
| `source_task_input_id` | UUID | Causal user input; unique within task and used as the idempotency mutex/identity. |
| `application_kind` | checked text: `patch` / `undo` | Distinguishes ordinary application from inverse application. |
| `request_schema_version` | positive integer | Selects the frozen parser for the application-kind request envelope. |
| `fingerprint_version` | positive integer | Selects structural canonicalisation. |
| `request_fingerprint` | lowercase SHA-256 | Detects identity reuse with different content. |
| `base_revision` | non-negative bigint | Exact CAS base. |
| `resulting_revision` | non-negative bigint | Equal to base for no-change; base + 1 for a mutation. |
| `outcome` | checked text: `applied` / `no_change` | Makes zero-mutation success explicit. |
| `delta_schema_version` | positive integer | Selects the exact applied-delta parser. |
| `applied_delta` | JSONB exact object | Server-generated, presentation-neutral retry and undo data. |
| `undoes_application_id` | nullable UUID | Same-task target; present only for undo. |
| `created_at` | database `timestamptz` | Durable receipt time. |

Required constraints:

- Unique `(task_id, id)` and unique `(task_id, source_task_input_id)`.
- Composite task/source-input foreign key with `ON DELETE RESTRICT`.
- Composite same-task self-foreign key for `undoes_application_id`.
- A partial unique index on `(task_id, undoes_application_id)` where non-null,
  so one application can be undone once.
- `patch` implies no undo target; `undo` implies an undo target and applied
  outcome.
- `no_change` implies `resulting_revision = base_revision`; `applied` implies
  `resulting_revision = base_revision + 1`.
- `no_change` implies an empty delta entry list; `applied` implies at least one
  entry.
- JSON object, delta entry-list, and schema-version discriminator agreement,
  plus fingerprint shape/version checks.
- `ON DELETE RESTRICT`; no receipt deletion workflow in V0-04.

There is no `pending` status. Locking the existing input row serializes retry
before receipt creation, so only a complete final receipt can commit. Rejected
patches create no receipt. A successful no-change does create one, preventing
ambiguous repeated processing of the same source.

The receipt is read only for idempotent result return, latest-change undo, and
diagnostics at this boundary. The exact idempotent result is the receipt identity,
outcome, base/result revisions, generated authoritative IDs, and stored delta.
If the caller also requests a brief after a later retry, it is projected as of
the receipt's resulting revision from criterion validity intervals; it is not
stored in the receipt. Current truth always comes from task, concept, and
criterion tables.

Receipt reads validate more than JSON shape: outcome/revision/delta coherence,
entry revisions against the receipt result, and task ownership of every
referenced concept, criterion, source, and undo target. A structurally valid
delta that points outside its task or disagrees with materialized rows is
`PersistedDataCorruptionError`, never trusted retry or undo input.

## Fingerprinting/versioning

Application fingerprint V1 covers exactly:

```text
{
  applicationSchemaVersion,
  applicationKind,
  expectedRevision as decimal string,
  source plan including referenced input IDs,
  raw StatePatchProposalV1 or raw UndoCommandV1
}
```

It excludes server task ownership already established by the scoped lookup,
receipt ID, generated concept/criterion/lineage/source IDs, timestamps,
resulting revision, canonical-unit conversion results, and applied delta.

Canonical JSON recursively sorts object keys and preserves array order. It does
not trim, case-fold, Unicode-normalise, reorder operations or categorical
values, convert units/currency, or reinterpret shopper text. Fingerprinting uses
the preserved, strictly structurally validated raw wire envelope before existing
Zod transforms or measurement normalization. It never accepts the output of a
transforming domain parser as its input. Therefore two accepted commands such as
`"Nike"` and `" Nike "` may canonicalise to the same stored domain value but
produce different V1 fingerprints. Local refs remain stable strings and
therefore do not depend on generated UUIDs. Arrays that are semantic sets, such
as `replacesCriterionIds`, are required to arrive in one validated sorted form;
the fingerprint canonicalizer itself does not reorder them.

Stored fingerprint versions select their historical canonicalizer on retry, as
V0-03 already does for `TaskInput`.

## Lifecycle, temporal, and cycle safety

The coordinator validates these invariants under the locked task row:

- Only an exact active criterion can be replaced, relaxed, tightened, removed,
  or consumed by indifference.
- A successor keeps the predecessor's task, lineage, and concept.
- `successor.createdRevision` and `predecessor.endedRevision` both equal the one
  new task revision and are strictly greater than predecessor creation.
- The successor ID is new and absent from the lineage.
- Traversing `supersededById` from the predecessor cannot encounter the new ID,
  repeat an ID, point backward in revision, or leave task/lineage/concept.
- The existing deferred foreign key and active-lineage partial index remain the
  commit-time structural backstop.
- Removed rows remain removed. A later restoration creates a new active version
  in the same lineage; it never rewrites the removed row.
- After the compiled patch, every affected lineage has at most one active row.
- Final active indifference is exclusive within its exact concept; ordinary
  multi-criterion concepts remain allowed.

Triggers are not planned. Application logic plus existing/new ordinary
constraints and concurrency tests are sufficient for this bounded coordinator.

## Undo model

### Boundary

Undo is a separate deterministic command, not an ordinary patch operation:

```ts
type UndoStateChangeCommandV1 = {
  applicationSchemaVersion: 1;
  applicationKind: "undo";
  taskId: ShoppingTaskId;
  expectedRevision: bigint;
  source: { kind: "user_explicit"; inputId: TaskInputId };
  targetApplicationId: StateChangeApplicationId;
};
```

The target must:

- belong to the same task;
- be a meaningful forward `patch` receipt, not `no_change` or another undo;
- have `resultingRevision === task.currentRevision`;
- be the latest meaningful state change (later no-change receipts do not block);
- have no existing undo receipt;
- still match the current materialized criterion state described by its delta.

This latest-applicable-change rule prevents undo from silently clobbering an
unrelated later change. Arbitrary history editing, undo-of-undo, and redo are
deferred.

### Transaction

Undo uses the same source-input lock, retry lookup, task lock, stale check, and
conditional CAS. It loads and validates the target receipt/delta under the task
lock, compiles the complete inverse before writes, advances exactly one new
revision, applies every inverse atomically, inserts an `undo` receipt whose
`undoesApplicationId` targets the original, and commits.

Retrying the same undo input returns its receipt. A different input attempting
to undo the same target gets a typed unavailable/already-undone failure. An undo
racing a forward patch is just two writers against one task revision: one wins
and the other is stale with zero mutation.

### Forward-history inverses

Undo never decrements `currentRevision`, deletes rows, switches an old row back
to active, or replays all receipts.

1. **Added criterion:** mark its current active version removed at the undo
   revision and add undo change provenance.
2. **Replace/relax/tighten:** supersede the current after-version with a newly
   allocated active row in the same lineage/concept whose strength, target, and
   semantic value copy the recorded before snapshot. Derive the new row's
   authority as `user_explicit` from the undo command. Preserve the restored
   meaning's validated historical origin/confirmation provenance and add the
   undo input as `change`; provenance history does not override the new version's
   explicit authorization.
3. **Removed criterion:** create a new active row in the same lineage/concept
   from the before snapshot, with authority `user_explicit` derived from the undo
   command. Preserve its validated historical origin/confirmation provenance and
   add the undo input as `change`. The removed row stays removed;
   lineage/revision history shows the gap and restoration.
4. **Marked indifferent:** remove the active indifference row and create new
   active versions in every prior lineage from the recorded before snapshots.
   Every undo-created version has `user_explicit` authority from the undo command
   while retaining validated historical origin/confirmation provenance and the
   undo input as `change`.
5. **Created concept plus criterion:** undo the criterion as above; retain the
   now-unused concept because deletion would destroy historical identity.
6. **Multi-operation patch:** compile inverses from delta entries in reverse
   order and apply the entire set in one revision/transaction. Because one
   forward patch cannot consume a lineage twice, inversion remains bounded.

The undo-created applied delta records what this undo changed; it does not erase
or replace the target receipt.

## Authoritative state-loading boundaries

Avoid one future-facing aggregate containing search state. Add two focused
boundaries:

```ts
type CurrentShoppingState = {
  task: ShoppingTask;
  concepts: readonly ConceptDefinition[];
  activeCriteria: readonly {
    criterion: DecisionCriterion;
    sources: readonly CriterionSource[];
  }[];
};
```

`loadCurrentShoppingState` is a read boundary for brief projection and later
consumers. It parses all task-owned rows, validates revision bounds,
canonical storage, provenance, active-lineage uniqueness, concept ownership,
and indifference exclusivity. It does not replay applications or messages.

`loadShoppingStateAtRevision` is the narrow historical view needed to reproduce
the brief associated with an idempotent receipt. It selects concepts with
`createdRevision <= revision` and criterion versions whose interval contains the
revision (`createdRevision <= revision` and no end, or `endedRevision >
revision`). Interval membership is authoritative regardless of the row's current
or final lifecycle label: a row now marked `superseded` or `removed` is still the
effective historical version at revision R when
`createdRevision <= R < endedRevision`. The historical loader must not reuse a
current-state `lifecycle === "active"` filter. It derives that snapshot from
materialized version rows, not receipt or message replay, and rejects a requested
revision above the task's current revision.

`loadTransitionContextInTransaction` is an internal locked write boundary. It
loads the task, exact source inputs/messages, affected concepts, exact active
targets, required histories, and existing receipt. Undo additionally loads one
target receipt and the criterion versions referenced by its delta. It does not
load future retrieval/application state.

Persisted receipt and delta reads receive the same fail-closed typed corruption
treatment as V0-03 mappers.

## Deterministic applied delta

The server returns and stores one exact `AppliedStateDeltaV1`:

```ts
type AppliedStateDeltaV1 = {
  schemaVersion: 1;
  entries: readonly AppliedDeltaEntryV1[];
};

type CriterionSnapshotV1 = {
  id: CriterionId;
  lineageId: CriterionLineageId;
  conceptId: ConceptDefinitionId;
  authority: CriterionAuthority;
  strength: CriterionStrength | null;
  targetSemantics: TargetSemantics;
  valueSchemaVersion: 1;
  valueKind: SemanticValueKind;
  semanticValue: SemanticValue;
  lifecycle: CriterionLifecycle;
  createdRevision: bigint;
  endedRevision: bigint | null;
  supersededById: CriterionId | null;
};
```

Entry kinds are deliberately domain-specific:

- `concept_created`
- `criterion_added`
- `criterion_replaced`
- `criterion_relaxed`
- `criterion_tightened`
- `criterion_removed`
- `concept_marked_indifferent`
- `criterion_restored_by_undo`
- `criterion_ended_by_undo`

Entries contain authoritative concept/criterion/lineage IDs and the exact
before/after durable snapshots required by that kind. An added entry has no
before and one active after. A replacement-like entry retains the predecessor
before, its superseded after-state, and the active successor. A removed entry
retains the row's active before, removed after-state, and no active successor.
The mark-indifferent entry contains every active before, every removed
after-state, and the new active indifference row. `concept_created` carries the
server-owned concept snapshot. Undo entries identify the target application.
Bigints use decimal strings in JSON storage.

The delta contains no presentation copy, confidence, inferred rationale, model
output, search data, or arbitrary metadata. It is returned immediately, stored
for exact retry and latest-change inversion, and parsed by version. Current truth
is never calculated from it.

## Deterministic brief projection

Use a two-step pure boundary:

```ts
type ShoppingBriefV1 = {
  schemaVersion: 1;
  taskId: ShoppingTaskId;
  revision: bigint;
  market: MarketContext;
  items: readonly BriefItemV1[];
};

type BriefItemV1 = {
  criterionId: CriterionId;
  lineageId: CriterionLineageId;
  conceptId: ConceptDefinitionId;
  conceptLabel: string;
  conceptDefinition: string;
  strength: CriterionStrength;
  targetSemantics: Exclude<TargetSemantics, "indifferent">;
  semanticValue: Exclude<SemanticValue, { kind: "indifferent" }>;
};
```

`projectShoppingBrief(currentState)`:

- consumes only task, task-local concepts, and active criteria;
- omits explicit indifference entirely from visible items;
- preserves exact hard/preference strength, target semantics, value variant,
  categorical operator, money mode/stretch, bounds, canonical units, and
  qualitative content;
- adds no confidence, importance, inferred heading, category, or prose;
- orders deterministically by concept creation revision/ID then criterion
  creation revision/ID.

`formatBriefItem(item, market)` produces bounded shopper language from the exact
variant and always considers operator and strength together. Examples include
“Around £30”, “Maximum £30”, “Around £30; up to £40 if materially better”, and
“No white” only for a hard categorical exclusion. A softer exclusion must use
preference-strength language rather than hard eligibility copy; categorical
`include` and `prefer` receive equivalent strength-aware treatment. “Dark
preferred” must not become an include-only requirement. Exact operator and
strength remain in `BriefItemV1`, so copy is never the only carrier of meaning.

The formatter uses reviewed currency metadata and canonical measurement units.
It never turns `around` into `ceiling`, drops a stretch condition, converts
`prefer` into include-only eligibility, or fabricates explanatory prose.

The brief is not persisted and is not another source of truth. Rebuilding it
after refresh requires no messages, receipts, or conversation replay. V0-04
does not render it in the V0-02 UI.

## PostgreSQL integration and concurrency test plan

Use the existing guarded PostgreSQL 17.6 disposable-database harness.

### Schema and migration

- Apply the complete migration history from empty and verify no pending pass.
- Introspect receipt keys, same-task FKs, unique source identity, partial unique
  undo target, revision/outcome checks, JSON discriminators, and private-schema
  revokes.
- Assert no product/candidate/search/reaction/trace/event tables appeared.

### Atomicity and lifecycle

- A five-operation patch creates dependent concepts/criteria and advances once.
- Failure in operation four leaves zero new concepts, criteria, sources,
  receipts, or task revision.
- Add, replace, relax, tighten, remove, and indifference produce exact histories,
  provenance roles, and deltas.
- Successor end/create revisions are equal and forward; non-active or cyclic
  targets fail with no mutation.
- A patch may keep multiple ordinary active criteria on one concept.
- Active indifference cannot coexist with ordinary active truth on that concept.
- Cross-task concept, criterion, source input, message, receipt, and undo targets
  fail.
- Raw receipt corruption fails closed on read.
- After a criterion is later superseded or removed, retrying an older receipt
  reconstructs its old brief from `createdRevision <= R < endedRevision`
  regardless of the row's current lifecycle label.
- Every criterion version created by undo has `user_explicit` authority from the
  undo input while retaining the restored meaning's validated historical
  origin/confirmation provenance plus the undo `change` source.

### CAS and idempotency races

Use two independent database connections and synchronization barriers rather
than timing guesses:

1. Both writers read task revision N and propose different valid patches.
2. Hold the first transaction after its lock so the second genuinely contends.
3. Release; exactly one commits revision N+1.
4. The loser gets `StaleTaskRevisionError`.
5. The loser leaves no concepts, criteria, sources, or receipt.

Also prove:

- two concurrent same-source/same-fingerprint applications return the same
  receipt, generated IDs, delta, revision, and brief;
- same source/application identity with different content conflicts, including
  after a successful no-change;
- a successful retry is returned before stale validation;
- an existing causal application identity returns or conflicts by fingerprint
  before a retry's altered missing or cross-task non-causal source/message can
  preempt idempotency; synchronization-barrier coverage also proves the
  post-source-lock receipt recheck closes the concurrent first-application race;
- no-change stores one receipt and never advances revision;
- malformed or stale proposals store no receipt;
- an undo racing a new forward change permits one N+1 winner only;
- two different inputs cannot undo the same target;
- retry after successful undo returns the same undo receipt/result;
- unrelated later meaningful state prevents undo of an older application;
- later no-change receipts do not prevent undo of the latest meaningful change.

## Expensive-to-undo decisions

### 1. Patch operation grammar

- **Decision:** closed domain operations with exact resulting targets; no JSON
  Patch and no semantic instructions.
- **Alternative:** generic path/value mutations or “make looser” commands.
- **Why smallest credible:** exact operations preserve domain boundaries and make
  validation/deltas/undo finite without implementing interpretation.
- **Revisit when:** a real accepted operation cannot be expressed as one exact
  target plus explicit existing IDs.

### 2. Application receipt/idempotency

- **Decision:** one receipt table, unique causal `TaskInput`, versioned raw
  fingerprint, and stored exact delta; lock the input instead of persisting a
  pending row.
- **Alternative:** treat `TaskInput` as an event, keep an in-memory retry cache,
  or build an event log.
- **Why smallest credible:** survives processes/restarts, returns generated IDs,
  serializes concurrent retries, and supports bounded undo without replay.
- **Revisit when:** one source input legitimately needs several independent
  authoritative applications; that would require explicit sub-application
  identity rather than weakening uniqueness silently.

### 3. Revision transaction ordering

- **Decision:** raw causal identity → authoritative receipt probe → stable source
  locks → receipt recheck → full source/message validation → task lock/check →
  compile all → CAS task to N+1 → child writes/receipt → commit.
- **Alternative:** CAS without a row lock, or child writes before task update.
- **Why smallest credible:** explains concurrency explicitly and composes with
  V0-03 child revision guards while remaining externally atomic.
- **Revisit when:** evidence shows task-level write serialization is a measured
  bottleneck; not before.

### 4. Undo

- **Decision:** only the latest applicable meaningful patch, atomically across
  its full delta, through a new forward revision; no undo-of-undo.
- **Alternative:** arbitrary time travel, row resurrection, revision decrement,
  or per-operation partial undo.
- **Why smallest credible:** protects unrelated later truth and preserves
  understandable lineage history.
- **Revisit when:** observed UX needs selective historical recovery and has a
  reviewed conflict model.

### 5. Criterion lineage continuation

- **Decision:** exact target version derives lineage/concept; replacements and
  restorations create new versions. Concept-level indifference removes explicit
  old lineages and starts one new indifference lineage.
- **Alternative:** one active criterion per concept or destructive overwrite.
- **Why smallest credible:** supports legitimate multi-criterion concepts while
  preserving complete history and indifference semantics.
- **Revisit when:** evidence shows indifference needs narrower-than-concept scope;
  that is a semantic-model change, not an implementation tweak.

### 6. Local references

- **Decision:** backward-only local refs for newly created concepts; no local
  criterion refs or DAG.
- **Alternative:** client-assigned UUIDs or a general dependency graph.
- **Why smallest credible:** supports atomic concept+criterion creation without
  exposing server entity assignment or complex execution planning.
- **Revisit when:** a required atomic operation genuinely depends on another new
  criterion's identity.

### 7. Brief projection

- **Decision:** exact structured `BriefItem` values plus a deterministic formatter;
  never persisted.
- **Alternative:** store prose or let an LLM summarize current truth.
- **Why smallest credible:** preserves semantics, remains inspectable, and
  rebuilds without replay while allowing later UI copy changes.
- **Revisit when:** user testing proves another deterministic presentation field
  is needed; authoritative criteria remain unchanged.

### 8. No-change persistence

- **Decision:** durable receipt, empty delta, equal base/result revision, no task
  update.
- **Alternative:** no durable record or an artificial revision.
- **Why smallest credible:** gives unambiguous retry semantics without inventing
  shopper truth or revision movement.
- **Revisit when:** never; a future trace may add diagnostics but must not turn
  no-change into semantic state.

Reversible choices that should not delay implementation include exact module
names, whether delta formatter helpers share a file, initial non-constraint
indexes, and whether a supported Drizzle builder or scoped SQL expresses
`FOR UPDATE` and the final CAS.

## Scope-leakage self-challenge

- The patch grammar contains exact structured outcomes, not an interpreter.
- Relax/tighten never calculate shopper meaning; only provably inverse labels
  are rejected.
- Ordinary concepts may have multiple active criteria; only indifference is
  structurally exclusive on its exact concept.
- The receipt is not replayed and contains no pending/event/trace workflow.
- Undo reads one latest receipt and exact referenced history, not all events.
- Undo creates forward versions and never decrements or resurrects rows.
- No-change leaves the task revision untouched.
- Unique causal input plus row lock prevents the same input mutating twice.
- Task lock plus CAS prevents two revision-N writers both succeeding.
- One transaction prevents partial multi-operation state.
- The proposal cannot assign authority, task ownership, IDs, revisions,
  lifecycle, sources, or timestamps.
- Every source and state reference is checked inside one task.
- Indifference is omitted from brief projection and has no ranking path.
- Structured brief values preserve around/ceiling/stretch and every other typed
  distinction before formatting.
- No product, candidate, reaction, search, observation, assessment, or judgement
  identity is introduced.
- No model call, question policy, or stale reinterpretation enters V0-04.
- The accepted V0-02 UI remains untouched.
- No category-specific field, conflict rule, or synonym matcher exists.

## Correction-pass self-review

- Historical retry briefs use criterion validity intervals independently of the
  row's current lifecycle label.
- Undo-created versions state their new `user_explicit` authorization while
  retaining, but not inheriting authority from, historical provenance.
- Existing causal application identity wins fingerprint return/conflict before
  altered non-causal source validation, with a locked recheck for concurrency.
- Fingerprint V1 consumes only the preserved non-transforming raw accepted wire
  envelope; transforming V0-03 schemas remain the semantic storage boundary.
- Categorical direction and criterion strength remain independent in both the
  narrow transition proof and shopper-facing formatting.
- No event sourcing, V0-05 interpretation, additional table, or implementation
  work entered this correction pass.

## Open questions

There are no blocking implementation questions after this plan. Independent
review should concentrate on the receipt's unique causal-input identity, the
CAS-before-child-write ordering, concept-level indifference transition, stored
delta sufficiency for undo, latest-applicable undo restriction, and the limited
relax/tighten contradiction guard. A finding that changes one of those decisions
should amend this plan before implementation; ordinary naming or file-layout
preferences should not.
