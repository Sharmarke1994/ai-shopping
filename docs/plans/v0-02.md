# V0-02 Fixture-Driven Consumer Shell

**Status:** Proposed execution plan
**Gate:** Gate 1 — visible product hypothesis
**Boundary:** UI fixtures only; no live AI, persistence, retrieval, provider, or semantic-engine implementation

## Objective

Build a polished, clickable consumer shopping prototype that lets us judge the
information hierarchy and answer the first product question: would someone
prefer to begin and refine a shopping decision here rather than in a chatbot,
filter form, or retailer-tab pile?

The shell must feel like a shopping product, not a developer dashboard. Fixture
records are presentation-only view models and must not become provisional
domain schemas.

## Product and visual hypothesis

- One continuous surface moves from request to task workspace; avoid a wizard,
  dashboard navigation, or chat transcript.
- Product imagery and decision-relevant trade-offs dominate once results exist.
- The brief makes the system's current understanding inspectable in shopper
  language without exposing confidence, ontology, queries, or model internals.
- Start with a warm off-white canvas, near-black type, restrained deep forest
  accent, fine neutral borders, locally bundled Newsreader display type and
  Inter UI type. Use generous space and restrained corners; avoid gradients,
  purple AI styling, glass effects, bubbly chat, and card-on-card clutter.
- Use stable local fixture imagery so visual review and screenshots are
  deterministic.

## Screen hierarchy

### 1. Landing

1. Quiet header: wordmark and a short trust cue; no category navigation.
2. Editorial hero: a sharp promise and one sentence explaining the benefit.
3. Dominant natural-language request field with a single primary action.
4. Three unrelated example journeys: running cap, slim shelving, and commuting
   headphones.
5. A brief non-affiliate/evidence trust note below the primary interaction.

Only prepared example requests advance during V0-02. Other text receives a
clear prototype limitation and an invitation to select a prepared journey; the
shell must never pretend that real interpretation or search occurred.

### 2. Task workspace

1. Compact global header: wordmark, **New search**, and saved count.
2. Task heading: the shopper's request and a low-emphasis refinement entry.
3. Inspectable brief: natural-language criteria grouped only by shopper-facing
   meaning such as **Must have**, **Preferences**, and **Flexible**.
4. Optional single-question panel. A post-result question appears above the
   result set without hiding existing products.
5. Result heading with plain-language framing, never a match percentage.
6. Product grid. Each card contains:
   - prominent image with deliberate fallback;
   - name, brand/merchant, and conservatively labelled observed price;
   - one grounded reason it may fit;
   - one meaningful trade-off, uncertainty, or evidence gap;
   - **Save**, **Not for me**, and **Open retailer** actions.
7. Contextual refinement composer after the result set on desktop and as a safe
   sticky action on mobile.

There is no comparison screen, product-detail architecture, task history, or
full saved-items workspace in V0-02.

## Fixture states

All states are deterministic and directly addressable for tests and screenshot
review.

| Fixture | What it tests |
| --- | --- |
| Landing, empty and typed | Promise, request dominance, examples, validation |
| Cap, pre-result question | One worthwhile question and **Show options now** |
| Shelving, results | Hard fit, flexible budget, visual preferences, honest unknown dimensions |
| Headphones, post-result question | Existing products remain visible while priorities change |
| Headphones, refined | Visible brief delta, retained save, and changed ordering without claiming real AI |
| Degraded results | Broken image fallback, unknown evidence, partial-result notice, and retry affordance |

Fixture copy should be realistic enough to judge card density and hierarchy,
but candidate and merchant identities must be clearly fictional or safely
licensed. Fixture-only types stay inside the preview feature and use names such
as `FixtureCandidateCard`, not `Product` or future domain contracts.

## Interactions

- Example selection or a prepared request opens its fixed journey.
- Question choices update the displayed fixture snapshot; **Show options now**
  skips without inventing an answer.
- Brief rows can be expanded and visually removed/restored within the fixture
  session so change-of-mind affordances can be judged.
- **Save** toggles visibly and updates the header count.
- **Not for me** removes only that card and exposes a nearby undo action; it
  creates no preference.
- Refinement submission swaps to a prepared refined snapshot, shows the applied
  change, retains saves, and changes results observably.
- **Open retailer** is visually testable but uses a safe fixture target.
- URL fixture parameters provide deterministic direct access for browser tests
  without exposing a developer toolbar in consumer screenshots.

These interactions are local preview state only and reload may reset them.

## Responsive behaviour

- **Wide desktop (1440 px):** sticky 280–320 px brief rail plus a product-led
  main column; three cards when width supports them.
- **Laptop/tablet (1024 px):** compact brief rail and two-card grid without
  shrinking decision copy below comfortable reading size.
- **Mobile (390 px):** one column; brief becomes an expandable summary before
  results; question stays inline; product actions have at least 44 px targets;
  refinement action remains reachable without covering content.
- No horizontal scrolling, hover-only meaning, clipped focus rings, layout
  jumps from image failures, or duplicated desktop/mobile interaction logic.

## Visual verification

1. Add deterministic component/interaction tests for prepared journeys, save,
   rejection/undo, question skip, refinement, and degraded results.
2. Add Playwright screenshot coverage at 1440×1000, 1024×768, and 390×844 for
   the landing, question, results, refined, and degraded states.
3. Review rendered screenshots manually for hierarchy, typography, image crop,
   spacing rhythm, density, product prominence, evidence honesty, focus states,
   tap safety, overflow, and sticky-element obstruction.
4. Exercise the journeys with keyboard-only navigation and reduced motion.
5. Iterate the visual direction from screenshot evidence; the initial palette
   and type treatment are hypotheses, not protected architecture.

## Delivery sequence

1. Create isolated fixture view models, scenarios, and direct fixture routing.
2. Build the landing hierarchy and prepared-journey transition.
3. Build the task shell, brief, question panel, result cards, and refinement
   composer.
4. Add local interactions and degraded-state behaviour.
5. Complete responsive and accessibility passes.
6. Capture, review, and iterate the screenshot matrix.
7. Run the full repository quality and browser gates and self-review against
   the exclusions below.

## Acceptance criteria

- All three unrelated journeys are coherent and clickable without credentials
  or external network calls.
- The landing is led by natural language rather than filters or categories.
- The brief is inspectable and mutable in shopper language.
- One question is shown at a time, can be skipped, and does not hide existing
  products post-search.
- Products visually dominate the workspace and every card presents a reason,
  a trade-off/evidence gap, and the required actions without scores or medals.
- Save, rejection/undo, prepared refinement, broken imagery, honest unknowns,
  and partial results have deliberate fixture behaviour.
- Desktop, laptop, and mobile screenshot reviews find no hierarchy, overflow,
  focus, tap-target, or sticky-obstruction failures.
- Automated formatting, linting, strict type checking, deterministic tests,
  production build, and browser checks pass.
- No real AI, prompt orchestration, persistence, retrieval, search adapter,
  provider configuration, observation/assessment logic, generic product domain
  schema, authentication, comparison, or affiliate behaviour is introduced.

V0-02 ends with a reviewable UI PR and screenshot evidence. Gate 2 semantic
engine work begins only after this product-hypothesis checkpoint is accepted.
