# V0-03 — Semantic domain and persistence foundation

## Status and objective

This is the implementation plan for the first Gate 2 code slice. V0-03 will add
the authoritative, task-scoped domain and PostgreSQL persistence foundation for
shopping tasks, input provenance, messages, task-local concepts, and decision
criteria. It will prove that the approved semantic distinctions survive typed
validation and storage round trips.

This plan does **not** authorize implementation. The implementation starts only
after independent review accepts the expensive schema decisions below.

V0-03 stops below the state-transition layer. V0-04 will own patch application,
conflict/supersession decisions, replace/relax/tighten/remove/indifferent
operations, undo, brief projection, and revision-changing orchestration. V0-03
must make those behaviours possible without implementing them early.

## Boundary

### In V0-03

- Versioned TypeScript and Zod contracts for semantic values, criterion
  dimensions, and market context.
- Explicit PostgreSQL schema and committed Drizzle-generated SQL migrations.
- Persistence for independently identified tasks, client inputs/idempotency,
  user messages, task-local concept definitions, criteria, and criterion
  provenance.
- A monotonic task revision token and historical criterion representation.
- Structural constraints at the strongest appropriate PostgreSQL layer.
- Concrete, feature-oriented data-access modules with transaction-aware methods.
- Credential-free domain tests and PostgreSQL integration/migration tests using
  an ephemeral local or CI database.
- Golden-case evidence for representation, ownership, provenance, lifecycle,
  idempotency, and lossless round trips.

### Not in V0-03

- No OpenAI calls, prompts, interpreter, ASK/SEARCH/SHOW logic, retrieval,
  provider integration, search hypotheses, product observations, assessments,
  judgements, ranking, candidate normalisation, page inspection, or merchant
  links.
- No patch application, semantic conflict resolution, lifecycle transition
  service, undo, brief projection, or presentation-state orchestration.
- No authentication, user/workspace/global memory, comparison UI, affiliate
  behaviour, vector database, queue, microservice, or broad trace/event system.
- No `Product`, `CandidateListing`, reaction, or other premature retrieval
  identity schema.
- No changes to the accepted V0-02 UI or its fixture contracts.

Messages and input records are retained as provenance. They are not replayed to
derive current truth, and this design is not event sourcing.

## Proposed domain records

| Record | Responsibility | Deliberate non-responsibility |
| --- | --- | --- |
| `ShoppingTask` | Aggregate identity, current revision, initial market context, and timestamps | It is not a singleton pointer to whichever task the UI happens to show. |
| `TaskInput` | One idempotent client submission, its expected revision, typed source snapshot, and canonical fingerprint | It is not an applied domain event or a record of a successful state transition. |
| `UserMessage` | User-authored conversation content attached to a task and its originating input | It is provenance, never a materialized statement of current requirements. |
| `ConceptDefinition` | Task-local meaning and compatible value family for an open-ended concept | It is not a shared ecommerce taxonomy, category field, or global ontology. |
| `DecisionCriterion` | One historical version of explicit or user-confirmed shopper truth | It cannot contain model-only inference, search hypotheses, or product evidence. |
| `CriterionSource` | Referential origin, confirmation, or change provenance for a criterion | It is not an unstructured explanation string. |

IDs are application/database-owned UUIDs. Domain code accepts opaque branded ID
types rather than interchangeable strings. All child records carry `task_id`,
even where it is transitively discoverable, so composite foreign keys can make
cross-task references structurally invalid.

## Proposed relational schema

The names are proposed now because renaming is cheap before migration review and
expensive after consumers exist. Exact Drizzle syntax remains an implementation
detail.

All application tables live in a dedicated `shopping_private` PostgreSQL schema,
not `public`. V0-03 accesses them only through the server-side Drizzle connection;
the schema is not added to Supabase's exposed Data API schemas, and migrations
explicitly revoke access from `anon` and `authenticated`. Supabase recommends
keeping internal tables in a non-exposed schema and using a dedicated API schema
only when an API surface is intended
([security guidance](https://supabase.com/docs/guides/api/securing-your-api),
[custom schemas](https://supabase.com/docs/guides/api/using-custom-schemas)).
Task ownership constraints provide data integrity, not authentication; V0-03
does not invent RLS identities before auth exists.

### `shopping_tasks`

| Column | Shape | Rule |
| --- | --- | --- |
| `id` | `uuid` | Primary key; generated server-side. |
| `current_revision` | `bigint` | Not null, starts at `0`, and must be non-negative. |
| `market_country` | `text` | Required ISO 3166-1 alpha-2 code. |
| `language_tag` | `text` | Required BCP 47 tag. |
| `currency_code` | `text` | Required uppercase ISO 4217 code. |
| `created_at`, `updated_at` | `timestamptz` | Database-generated UTC instants. |

GB / `en-GB` / GBP is supplied by one versioned application
`DEFAULT_MARKET_CONTEXT` at task creation. These values are not repeated as
column defaults or checks, so another market is an input change rather than a
migration.

There is no `current_task` table and no user owner in V0-03. Each route or later
service must receive a task ID explicitly.

### `task_inputs`

| Column | Shape | Rule |
| --- | --- | --- |
| `id`, `task_id` | `uuid` | Primary key plus composite task ownership. |
| `client_action_id` | `text` | Non-empty client-generated idempotency key; unique with `task_id`. |
| `input_kind` | checked `text` | V0-03 closed transport kinds: `message`, `question_answer`, `direct_brief_action`. |
| `input_schema_version` | positive integer | Selects the typed input snapshot parser. |
| `input_payload` | `jsonb` object | Validated typed source snapshot, not semantic truth. |
| `fingerprint_version` | positive integer | Selects the frozen structural canonicalizer used for this row. |
| `request_fingerprint` | fixed lowercase SHA-256 text | Fingerprint of the versioned canonical kind/input-schema/source-content/expected-revision envelope. |
| `expected_revision` | `bigint` | Exact non-negative revision observed by the client. |
| `received_at` | `timestamptz` | Database-generated. |

The unique key is `(task_id, client_action_id)`, not global. An insert with the
same key and fingerprint returns the existing input; the same key with different
content is an explicit idempotency conflict. This fingerprint check is a
deliberate strengthening of the original brief: uniqueness alone could silently
return the result of a different request after a client bug or key reuse.

Fingerprint V1 computes SHA-256 over a UTF-8 canonical JSON envelope with fixed
field names, recursively sorted object keys, preserved array order, and an
explicit `fingerprintVersion`. This is structural canonicalisation only. It does
not trim, case-fold, Unicode-normalise, collapse whitespace, convert units or
currency, reorder user selections, or reinterpret user text. A content change
such as `white` to `White` or one extra space is therefore a different request,
even if later semantic interpretation might consider the meanings related.

New inputs use the current fingerprint version. On a duplicate key, the adapter
loads the stored row and recomputes the incoming envelope with that row's frozen
canonicalizer before comparing. Old canonicalizers remain available while their
rows can be retried. A new input schema or genuinely different source content is
a conflict under the existing client action ID, not silently upgraded to a new
fingerprint meaning.

`input_payload` has its own small, versioned Zod union. It preserves the user
source needed for inspection—a message discriminator, selected question/option
snapshot, or direct brief action snapshot—but does not contain criteria or an
applied patch. The message variant duplicates neither an ID nor body: the unique
same-task `UserMessage.task_input_id` relation supplies the durable content, and
both records are created atomically. The request fingerprint covers the complete
structurally canonical incoming envelope, including that unmodified body. V0-04
can extend the union with new versions rather than retroactively changing old
provenance.

### `user_messages`

| Column | Shape | Rule |
| --- | --- | --- |
| `id`, `task_id` | `uuid` | Primary key plus composite task ownership. |
| `task_input_id` | `uuid` | Required; unique with `task_id`; composite reference to a same-task `message` input. |
| `body` | `text` | Non-empty user-authored text. |
| `received_at_revision` | `bigint` | The exact revision seen when submitted; non-negative. |
| `created_at` | `timestamptz` | Database-generated. |

The database can enforce same-task ownership and uniqueness. The persistence
adapter additionally verifies that the referenced input kind is `message` and
that its expected revision equals `received_at_revision`; a cross-row trigger is
not justified for this first slice.

Add a supporting unique key on `(task_id, task_input_id, id)`. Message provenance
uses that complete identity, so a source cannot pair one task input with a
different message merely because both happen to belong to the same task.

### `concept_definitions`

| Column | Shape | Rule |
| --- | --- | --- |
| `id`, `task_id` | `uuid` | Primary key and task-scoped composite identity. |
| `label` | `text` | Required human-facing name. |
| `definition` | `text` | Required concise task-local meaning. |
| `value_family` | checked `text` | `boolean`, `qualitative`, `measurement`, `money`, or `categorical`. |
| `canonical_unit` | nullable `text` | Required only for measurement concepts; validated against the unit registry. |
| `created_revision` | `bigint` | Non-negative revision at which the concept becomes available. |
| `created_at` | `timestamptz` | Database-generated. |

There is no category column and no global uniqueness rule on label or meaning.
Identity is unique only as `(task_id, id)`. The small set of value families is a
closed serialization grammar, not a list of shopping concepts. Reusing an
existing concept by meaning is V0-04 application logic; V0-03 must not guess that
two labels are synonymous.

### `decision_criteria`

| Column | Shape | Rule |
| --- | --- | --- |
| `id`, `task_id` | `uuid` | Primary key and task ownership. |
| `lineage_id` | `uuid` | Stable identity across later replacement versions. |
| `concept_id` | `uuid` | Composite foreign key to a same-task concept. |
| `authority` | checked `text` | `user_explicit` or `user_confirmed`. |
| `strength` | nullable checked `text` | `hard`, `strong_preference`, or `preference`; null only for indifference. |
| `target_semantics` | checked `text` | `exact`, `range`, `around`, `stretch`, `categorical`, `qualitative`, `comparative`, or `indifferent`. |
| `value_schema_version` | positive integer | Selects the persisted semantic-value parser. |
| `value_kind` | checked `text` | Duplicates the JSON discriminator deliberately for constraints and migrations. |
| `semantic_value` | `jsonb` object | Complete versioned union payload, always parsed at the boundary. |
| `lifecycle` | checked `text` | `active`, `superseded`, or `removed`. |
| `created_revision` | `bigint` | Revision that introduced this version. |
| `ended_revision` | nullable `bigint` | Required for non-active rows and greater than or equal to `created_revision`. |
| `superseded_by_id` | nullable `uuid` | Same-task, same-lineage, same-concept criterion reference; set only for `superseded`. |
| `created_at`, `updated_at` | `timestamptz` | Database-generated UTC instants. |

A partial unique index on `(task_id, lineage_id) WHERE lifecycle = 'active'`
prevents two active versions of one known criterion lineage. PostgreSQL cannot
infer whether two separately created, dynamic concepts conflict semantically;
V0-04 must detect that under a task lock and choose the lineage deterministically.
The schema should not pretend a label-based unique index solves semantic
identity.

Add a supporting unique key on `(task_id, lineage_id, concept_id, id)`. The
composite self-foreign-key
`(task_id, lineage_id, concept_id, superseded_by_id)` must be `DEFERRABLE
INITIALLY DEFERRED`, so a successor is structurally in the same task, lineage,
and concept. V0-04 can then update the old row away from `active` using the
already allocated successor UUID and insert the new active row in the same
transaction; the foreign key is checked at commit. Without deferral, the
successor reference and partial active-lineage index create an impossible
insert/update ordering. Both mechanisms are native PostgreSQL constraints rather
than ORM-only assumptions
([constraints](https://www.postgresql.org/docs/current/ddl-constraints.html),
[partial indexes](https://www.postgresql.org/docs/current/indexes-partial.html)).

Lifecycle checks require:

- `active`: no `ended_revision` and no successor;
- `superseded`: an end revision and a different same-task successor;
- `removed`: an end revision and no successor.

History is retained in rows; no criterion is overwritten into a new meaning and
no lifecycle operation hard-deletes it.

For a replacement, V0-04 must set
`predecessor.ended_revision = successor.created_revision` to the one newly
committed task revision. It must also require the successor revision to be later
than the predecessor's creation revision and reject a successor already present
in that lineage's predecessor chain. The same-concept foreign key, non-self
check, and revision shape are ordinary database constraints where possible;
cross-row temporal ordering and cycle prevention belong to the V0-04
transactional coordinator and integration tests, not a V0-03 trigger.

### `criterion_sources`

| Column | Shape | Rule |
| --- | --- | --- |
| `id`, `task_id` | `uuid` | Primary key and task ownership. |
| `criterion_id` | `uuid` | Composite foreign key to a same-task criterion. |
| `source_role` | checked `text` | `origin`, `confirmation`, or `change`. |
| `source_kind` | checked `text` | `message`, `question_answer`, or `direct_brief_action`. |
| `task_input_id` | `uuid` | Required composite reference to the same-task typed input snapshot. |
| `message_id` | nullable `uuid` | Required only for `message`; paired with `task_input_id` in an exact-source composite foreign key. |
| `created_at` | `timestamptz` | Database-generated. |

A criterion can have multiple source rows, so a model-originated proposal that
the user confirms records the user confirmation without rewriting its history.
V0-03 stores only criteria whose final `authority` is user-confirmed or explicit;
it has no persistence route for unconfirmed inference. A uniqueness constraint
on `(criterion_id, source_role, task_input_id)` prevents duplicated provenance.

For a message source, the composite foreign key
`(task_id, task_input_id, message_id)` references
`user_messages(task_id, task_input_id, id)`. PostgreSQL therefore proves that the
message is the record created by that exact input, not merely another message in
the same task. The adapter still checks that `TaskInput.input_kind` agrees with
`CriterionSource.source_kind`; this type agreement does not justify a trigger.

An explicit criterion requires an `origin` source. A confirmed criterion requires
both an `origin` pointing to the user source material from which the proposal was
derived and a `confirmation` pointing to the answer/action that authorized it.
This retains useful origin and confirmation provenance without persisting model
transcripts as truth or introducing trace infrastructure. Because source rows are
children inserted in the same transaction, V0-03 enforces required source-role
sets in the persistence adapter and integration tests rather than a trigger.

## Revision model

`shopping_tasks.current_revision` is the sole authoritative concurrency token.
It begins at zero and moves by exactly one only when V0-04 successfully commits
an authoritative state patch. A later write will execute a compare-and-swap in
the same PostgreSQL transaction:

```text
UPDATE shopping_tasks
SET current_revision = current_revision + 1, updated_at = now()
WHERE id = :task_id AND current_revision = :expected_revision
RETURNING current_revision
```

Zero returned rows means stale input. `TaskInput.expected_revision` retains the
exact client expectation, but recording an input or message does not itself
advance semantic state.

V0-03 does not add a `task_revisions` or event table. Criterion
`created_revision` / `ended_revision` columns explain which persisted versions
were current without claiming to record every action. V0-04 will add the
transactional coordinator and may add a compact patch-result record if returning
the same result on retry requires it. Diagnostic traces remain a separate later
concern.

V0-03 exposes no production data-access function that can assign or decrement
`current_revision`; task creation initializes it to zero. The V0-04 compare-and-
swap statement becomes the only production revision mutation path and can only
advance by one.

V0-03 data-access functions that write concepts or criteria accept a caller-owned
transaction and an explicit revision; they do not begin a transaction or bump
the task. They stay internal until V0-04 provides the aggregate write service.
Integration fixtures may seed revisions directly, but no production endpoint is
added in this slice.

## Typed semantic value grammar

### TypeScript and Zod boundary

Use a top-level `schemaVersion: 1` plus `kind` discriminated union. Each variant
is a named exact object schema; unknown keys are rejected. No semantic API accepts
`Record<string, unknown>` or casts parsed JSON into a domain type.

The first union contains these shapes conceptually:

| `kind` | Required payload | Intended distinctions |
| --- | --- | --- |
| `boolean` | `value: boolean` | Exact yes/no truth. |
| `qualitative` | either typed text, or `relation` + typed anchor | “Visually light”, “low physical bulk”, and ordinal more/less intent without inventing a numeric scale. |
| `measurement` | decimal-string amount + registered unit | A number and unit without JavaScript floating-point loss. |
| `measurement_range` | optional lower/upper bounds, inclusivity, and one registered unit | Bounded or one-sided physical ranges; at least one bound is required and lower cannot exceed upper. |
| `money` | `mode: target` or `ceiling`, integer minor units, and currency | A flexible target remains different from a hard maximum through mode, target semantics, and strength. |
| `money_stretch` | target and greater conditional ceiling in the same currency, plus a concise user condition | “£30, stretch to £40 if materially better” is one structured intent, not two lossy budget numbers. |
| `categorical` | `operator: include`, `prefer`, or `exclude`; non-empty normalized display values | Inclusion, preference, and exclusion remain explicit. |
| `comparison` | typed relation plus a task-scoped known-candidate reference | Relative intent only when a real candidate identity exists. |
| `indifferent` | no value payload | Explicit openness; never a stand-in for missing data. |

The proposed V1 wire/storage shapes are deliberately concrete:

```text
{ schemaVersion: 1, kind: "boolean", value: boolean }
{ schemaVersion: 1, kind: "qualitative", mode: "text", text: string }
{ schemaVersion: 1, kind: "qualitative", mode: "ordinal",
  relation: "more" | "less" | "at_least" | "at_most", anchor: string }
{ schemaVersion: 1, kind: "measurement", amount: DecimalString, unit: UnitCode }
{ schemaVersion: 1, kind: "measurement_range",
  lower?: { amount: DecimalString, inclusive: boolean },
  upper?: { amount: DecimalString, inclusive: boolean }, unit: UnitCode }
{ schemaVersion: 1, kind: "money", mode: "target" | "ceiling",
  amountMinor: SafeInteger, currency: CurrencyCode }
{ schemaVersion: 1, kind: "money_stretch", targetMinor: SafeInteger,
  stretchCeilingMinor: SafeInteger, currency: CurrencyCode, condition: string }
{ schemaVersion: 1, kind: "categorical",
  operator: "include" | "prefer" | "exclude", values: NonEmptyString[] }
{ schemaVersion: 1, kind: "comparison",
  relation: "more_than" | "less_than" | "similar_to",
  reference: { kind: "candidate_listing", taskId: ShoppingTaskId,
               candidateListingId: CandidateListingId } }
{ schemaVersion: 1, kind: "indifferent" }
```

All strings are trimmed, length-bounded, and non-empty where present. Ranges need
at least one bound; two bounds must be ordered after unit normalization. Money
amounts are non-negative safe integers and stretch ceiling must exceed target.
Categorical values are de-duplicated by a documented case-folded comparison while
preserving the user's display text. The initial measurement registry need support
only the reviewed dimensions (`mm`, `cm`, `m`, `g`, `kg`) and is extended through
a code/schema review when a real case needs another dimension.

Money uses integer minor units and uppercase ISO 4217 currency codes. A small
currency metadata module validates minor-unit scale; the task currency must match
unless a later explicitly supported conversion exists. Measurements use a
versioned unit registry and normalize to the concept's canonical unit before
storage. The registry is extensible code/data, not an ecommerce ontology or a
database enum. Decimal quantities remain canonical decimal strings at the domain
boundary.

### Compatibility matrix

The criterion parser validates the record and value together:

| Concept family | Allowed value kinds / target semantics |
| --- | --- |
| `boolean` | `boolean` + `exact`; or `indifferent` |
| `qualitative` | `qualitative` + `qualitative`; or `comparison` / `indifferent` |
| `measurement` | `measurement` + `exact` / `around`, `measurement_range` + `range`, or `comparison` / `indifferent` |
| `money` | `money(target)` + `around` / `exact`, `money(ceiling)` + `range`, `money_stretch` + `stretch`, or `indifferent` |
| `categorical` | `categorical` + `categorical`, or `indifferent` |

Additional cross-field rules keep dimensions independent:

- `indifferent` requires target `indifferent`, null strength, and the explicit
  indifference value; omission creates no criterion row at all.
- Every non-indifferent criterion requires a strength.
- Categorical operator expresses direction; criterion strength expresses how
  binding that direction is. `exclude + hard` means disallowed, while
  `exclude + preference` or `exclude + strong_preference` means avoid if
  practical at the stated intensity. `prefer` accepts preference or strong
  preference. A hard positive membership rule uses `include + hard`; `include`
  may also carry a softer strength when it describes a favoured set. The parser
  rejects `prefer + hard` as internally contradictory, but never derives or
  upgrades strength merely from `include`, `prefer`, or `exclude`.
- Money `ceiling` is a one-sided `range` target, not the same value as a flexible
  target. Conditional stretch has its own payload and `stretch` target.
- `value_schema_version`, `value_kind`, and the JSON discriminators must agree.

### JSONB storage discipline

JSONB is used because future concepts are open-ended while the value grammar is
versioned. It is not an escape hatch. PostgreSQL checks that the value is an
object, its version and kind agree with scalar columns, and required
indifference/lifecycle combinations are valid. Every write parses the complete
domain object before SQL; every read parses the stored object and fails with a
typed data-corruption error rather than returning partially trusted data.
Migrations introduce a new parser/version before any writer emits it, and old
parsers remain available until stored rows are migrated deliberately.

### Accepted known-candidate comparison deferment

The TypeScript grammar can define the future comparison variant with a branded
reference containing `taskId` and `candidateListingId`, and unit tests can reject
a task mismatch. V0-03 should **not persist comparison criteria yet**. Without a
real `CandidateListing` table, PostgreSQL cannot prove that the referenced UUID
exists or belongs to the task; embedding a task ID in JSON only proves what the
payload claims. A generic product/reference table created solely to satisfy this
foreign key would be the placeholder product schema the architecture forbids.

The independently reviewed boundary is to ship the typed comparison contract but
make the V0-03 criterion persistence boundary return an explicit
`candidate_identity_not_available` error for that variant. When candidate
identity is designed, add `(task_id, candidate_listing_id)` ownership and a
composite foreign key before enabling writes. The golden comparison case is
therefore a contract-level same-task rejection in V0-03 and a database ownership
test later. This deferment is accepted and frozen for V0-03; the implementation
must not reopen it by weakening the guarantee or creating a placeholder table.

## Criterion dimensions remain independent

The columns and source relation intentionally do not derive one dimension from
another:

- **Authority** says who made the truth authoritative: `user_explicit` or
  `user_confirmed`.
- **Provenance** points to typed task input/message records and describes whether
  that source originated, confirmed, or changed the criterion.
- **Strength** says hard requirement/exclusion, strong preference, or preference.
- **Target semantics** says how the value is interpreted: exact, range, around,
  stretch, categorical, qualitative, comparative, or indifferent.
- **Lifecycle** says whether that historical row is active, superseded, or
  removed.

For example, “maximum £30” is `hard` + `range` + money ceiling; “around £30” is a
`preference` + `around` + money target; and “£30, stretch to £40 if materially
better” is a preference + `stretch` + money-stretch value. No single `budget`
column can collapse those meanings.

## PostgreSQL constraints and application checks

### Structural PostgreSQL guarantees

- Composite unique keys `(task_id, id)` on task-owned records support composite
  same-task foreign keys for concepts, criteria, inputs, messages, sources, and
  successor criteria.
- Unique `(task_id, client_action_id)` enforces idempotency identity; a checked
  fingerprint version/format and version-aware adapter comparison detect payload
  mismatch without changing historical retry identity.
- Non-negative revisions, positive schema versions, non-empty text, currency and
  country formats, timestamp defaults, and JSON object/discriminator agreement
  are checks.
- Closed serialization/lifecycle/authority/strength/source discriminators use
  text checks rather than PostgreSQL enum types, keeping migrations reversible.
  Dynamic concept names and values are never encoded as SQL enums.
- Partial unique active-lineage index and lifecycle/end/successor checks prevent
  two active versions of one lineage and invalid historical shapes.
- The same-task, same-lineage, same-concept successor self-foreign-key is deferred
  until transaction commit, allowing an atomic old-version/new-version
  replacement without weakening the active-lineage uniqueness rule.
- Composite foreign keys prevent a source message, concept, criterion successor,
  or provenance input from belonging to another task. The message-source foreign
  key additionally proves that `message_id` belongs to the exact referenced
  `task_input_id`.
- Foreign keys use `ON DELETE RESTRICT`. V0-03 exposes no production hard-delete
  workflow; test cleanup uses a guarded test database. Retention/privacy-driven
  task deletion can later be designed as an explicit aggregate operation.
- Database-generated `timestamptz` values are authoritative; application clocks
  are not accepted for persistence timestamps.

### Application/transaction guarantees

- Full Zod parsing, concept/value compatibility, currency/unit compatibility,
  input-kind/source-kind agreement, and frozen versioned structural fingerprint
  calculation without semantic text normalisation.
- Same idempotency key + different fingerprint is a conflict, not a successful
  retry.
- `created_revision` / `ended_revision` cannot exceed the task revision selected
  under the future transaction lock.
- V0-04 replacement writes assign the same new revision to predecessor end and
  successor creation, move strictly forward, and reject lineage cycles.
- Semantic conflict across different lineages, concept reuse by meaning, and all
  lifecycle transitions are deferred to V0-04 because they require domain
  judgement and transactional current-state context.
- Candidate comparison existence/ownership remains disabled until a real
  candidate identity can supply a composite foreign key.

Triggers are avoided unless migration tests prove a critical invariant cannot be
kept by a normal constraint or the V0-04 transaction coordinator. In particular,
the database should not implement semantic inference.

## Drizzle and Supabase boundary

### Repository layout

```text
src/domain/shopping-state/
  ids.ts
  market-context.ts
  semantic-value.ts
  task.ts
  task-input.ts
  concept-definition.ts
  decision-criterion.ts
src/infrastructure/database/
  clients.ts
  migrate.ts
  schema/
    shopping-tasks.ts
    task-inputs.ts
    user-messages.ts
    concept-definitions.ts
    decision-criteria.ts
    criterion-sources.ts
src/features/shopping-state/persistence/
  tasks.ts
  inputs-and-messages.ts
  concepts.ts
  criteria.ts
drizzle/
  <generated SQL and migration metadata>
```

Domain modules know Zod and semantic types but not Drizzle. Database schema owns
SQL shape. Feature persistence modules map explicitly between the two; there is
no generic repository/base DAO.

The Drizzle TypeScript schema is the code-first source for every structure it can
represent exactly, and `drizzle-kit generate` is the normal source of reviewed SQL
committed under `drizzle/`. The committed migration history is authoritative for
the final physical PostgreSQL shape. Implementation must never use
`drizzle-kit push` against shared or production databases. An empty-database
migration test applies the complete committed history. This follows Drizzle's
distinction between
[generated SQL migrations](https://orm.drizzle.team/docs/drizzle-kit-generate)
and the application/runtime migration path
([migration overview](https://orm.drizzle.team/docs/migrations)).

If Drizzle's schema/generator cannot express required DDL exactly—including the
deferred composite successor foreign key, schema grants/revokes, or another
reviewed PostgreSQL constraint—use Drizzle's supported
`drizzle-kit generate --custom --name=<purpose>` flow and commit that custom SQL
inside the same migration history
([custom migration guidance](https://orm.drizzle.team/docs/kit-custom-migrations)).
Do not weaken the invariant to satisfy the ORM, and do not hand-edit an ordinary
generated migration in a way that makes its snapshot/metadata claim a different
shape. Migration integration tests inspect the resulting PostgreSQL constraints,
deferrability, indexes, and privileges rather than assuming the TypeScript schema
captured custom DDL.

The first migration creates `shopping_private`, keeps it out of the Supabase Data
API, revokes client-facing roles, and creates every table with schema-qualified
names. Migration history has one owner; Supabase CLI migrations are not run in
parallel with the Drizzle history. Migrations run as an explicit release command,
never implicitly during application import, request handling, or server startup.

### Connections and transaction ownership

- `DATABASE_URL` is validated only when application persistence is invoked. A
  Supabase transaction-pooler URL is suitable for serverless runtime, with
  prepared statements disabled as Supabase requires for transaction mode.
- `DIRECT_DATABASE_URL` is separately required only by migration commands. Use a
  direct connection (or documented session pooler where IPv4 makes direct access
  impossible), not a transaction pooler, for migrations.
- `TEST_DATABASE_URL` is required only by database integration tests and must
  target a visibly dedicated test database. Unit/component/UI tests remain
  credential-free.
- Client construction is explicit and lazy. Importing a domain module or running
  fixture UI tests cannot validate a database variable or open a connection.
- Persistence functions accept an existing Drizzle transaction when composing
  writes. V0-04 will own one transaction that locks/checks the task revision,
  writes new historical rows, closes prior rows, and advances the revision.

Supabase documents direct connections for native commands and migrations and
transaction pooling for serverless traffic; transaction mode does not support
prepared statements ([connection guidance](https://supabase.com/docs/guides/database/connecting-to-postgres)).

## Deterministic local and CI database testing

V0-03 relies on PostgreSQL features—JSONB checks, partial indexes, composite
foreign keys, transaction semantics—and will not substitute SQLite.

### Local contract

- Keep `pnpm test` and `pnpm check` free of external credentials and database
  startup. They run pure domain/Zod/mapping tests plus all existing V0-02 tests.
- Add an explicit `pnpm test:db` that requires `TEST_DATABASE_URL` and refuses a
  database whose name does not match a guarded test-only convention.
- Provide a minimal single-PostgreSQL-service configuration, not the full local
  Supabase stack. A developer may use that container or any disposable local
  PostgreSQL URL with the confirmed project major version. The full Supabase CLI
  stack requires a Docker-compatible runtime and is unnecessary for this slice
  ([Supabase local development](https://supabase.com/docs/guides/local-development)).
- The current workstation has no Docker-compatible runtime, `psql`, or Supabase
  CLI available. That does not affect planning or credential-free tests, but
  implementation must satisfy this explicit preflight before local DB integration
  tests can pass rather than discovering it after schema work.

### Test isolation

The DB test harness creates a uniquely named disposable database for one test
run, applies the committed migrations from empty, runs integration files
serially, and drops it in `finally`. Tests reset owned tables between cases with a
guarded truncate inside that disposable database; transaction-focused tests use
one passed transaction and rollback/savepoints. Random UUIDs provide row-level
isolation but are not the cleanup mechanism. Connection pools are closed before
drop.

The suite covers:

- migration from a completely empty database and a no-pending-migration check;
- schema introspection proving required custom DDL exists, including the deferred
  successor foreign key, exact-message/input provenance key, indexes, and
  client-role revokes;
- valid insert/read/parse round trips for every enabled value variant;
- raw invalid SQL attempts to prove database constraints rather than only Zod;
- rollback atomicity across input/message/provenance writes;
- same-key/same-fingerprint retry, same-key/different-content conflict,
  structurally reordered-object equivalence, text-preserving differences, and a
  historical V1 retry after a newer fingerprint version becomes current;
- composite foreign-key attempts across two tasks;
- a same-task provenance attempt pairing a message with the wrong input;
- partial active-lineage uniqueness, a rejected cross-concept successor, and all
  database-valid/invalid lifecycle shapes;
- database-owned timestamp presence and revision bounds.

### CI contract

Add a separate `persistence` job with a pinned PostgreSQL image/digest, health
check, ephemeral credentials, migration step, and `pnpm test:db`. GitHub supports
PostgreSQL service containers directly for jobs
([GitHub Actions guidance](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers)).
The existing quality and browser jobs remain independent of the database.

At implementation preflight, query the provisioned Supabase project's actual

## Golden-case acceptance map

### Running cap

- Persist `light` and `breathable` as two explicit task-local concepts/criteria
  sourced to the original user message; querying active criteria returns no
  colour, budget, or brand row.
- Persist a later Nike categorical `prefer` criterion with preference strength;
  no operator/value can round-trip as Nike-only/exclude-other-brands.
- Represent low physical bulk as a qualitative construction criterion. `race cap`
  is not persisted as a criterion merely because it could be a search phrase.

### Shelving

- Round-trip three distinct money fixtures: target £30 + `around`, ceiling £30 +
  hard/range, and target £30 / conditional £40 + `stretch`.
- Persist `no white` as categorical exclusion and dark as categorical preference,
  retaining distinct strengths.
- In a separate grammar fixture, prove that `rather avoid white` is
  `exclude + preference`, not silently upgraded to the hard `no white` meaning.
- Persist the stated maximum width and depth as two independent measurement
  concepts/criteria. Do not create a height criterion because the shopper did not
  provide one.
- Attempt to attach one task's concept, message, or criterion source to the other
  task and assert composite foreign-key failure.

### Headphones

- Round-trip over-ear categorical form, flexible £150 money target,
  glasses/clamp qualitative comfort, and ANC preference as independent records.
- Persist brand indifference with `strength = null`, indifferent target/value,
  and provenance. A separate omitted-brand fixture has no brand criterion row.
- Assert that colour, microphone, codec, battery, and ecosystem remain absent.

### Cross-cutting

- Two tasks with similar concepts retain different IDs and cannot share
  authoritative criteria, messages, or provenance through foreign keys.
- Omitted colour creates no row; explicit colour indifference creates a typed row.
- User-confirmed criteria have a confirmation source; no unconfirmed-inference
  authority or input kind is accepted.
- A message source cannot combine one same-task input with another same-task
  message; the exact-source composite foreign key rejects it.
- Same client ID within a task is idempotent only for the same fingerprint; it is
  independently usable in another task. Stored fingerprint versions preserve
  historical retry behaviour without normalising user text.
- Active, superseded, and removed history shapes round-trip without deletion, and
  a duplicate active lineage or cross-concept successor fails.
- All enabled value kinds survive write/read/Zod parsing without losing mode,
  units, currency, bounds, condition, operator, authority, strength, target, or
  provenance.
- Comparison parsing rejects a reference declaring another task. Persistence of
  even same-task comparison remains intentionally disabled until the candidate
  composite foreign key exists; this is an explicit acceptance exception, not a
  silently weakened database test.

These tests seed historical rows at known revisions. They do not implement patch
transitions, supersession choice, or undo to manufacture V0-04 coverage.

## Expensive-to-undo decisions for independent review

1. **Task is the aggregate and scope key.** Composite task ownership throughout
   prevents a future singleton/global-preference shortcut.
2. **One revision counter, no revision event log.** This fixes the concurrency
   boundary while avoiding premature event sourcing.
3. **Criterion versions use lineage plus lifecycle rows.** Replacements preserve
   history; a lineage is structurally bound to one task and concept, and the
   active partial index operates only within that identity.
4. **Semantic JSON is a versioned exact union.** Scalar version/kind columns and
   full read/write parsing prevent JSONB soup while allowing open concepts.
5. **Provenance is relational and one-to-many.** Typed task inputs plus source
   roles preserve origins and confirmations without treating messages as truth;
   message provenance is bound to its exact originating input.
6. **Idempotency is task-scoped identity plus a versioned content fingerprint.**
   This prevents both duplicate work and silent key reuse with different content
   without letting future canonicalisation break historical retries.
7. **Concept identity is task-local and not label-unique.** No global ontology is
   smuggled into the schema.
8. **Comparison persistence is disabled pending real candidate identity.** This
   independently accepted boundary is safer than an unverifiable JSON reference
   or placeholder product table.
9. **Production foreign keys restrict deletion.** A future privacy deletion flow
   must deliberately delete the aggregate rather than depending on accidental
   cascades.
10. **Authoritative state uses a non-exposed database schema.** Server-owned
    tables do not become a Supabase Data API by placement or default grants; a
    later client API must be designed explicitly.
11. **Committed migration history owns the physical database shape.** Drizzle
    generation is normal, while supported custom migrations retain reviewed
    PostgreSQL guarantees the TypeScript schema cannot express exactly.

Reversible choices that should not block progress include individual file names,
whether closely related schema files are combined, exact function names, initial
index tuning beyond constraints, the Drizzle-compatible PostgreSQL driver, and
whether a developer points `TEST_DATABASE_URL` at the supplied single container
or another disposable local PostgreSQL instance.

## Self-challenge result

- No universal product schema, category-specific column, or candidate placeholder
  was introduced.
- JSONB contains only versioned, exact, fully parsed unions; no arbitrary semantic
  record crosses the boundary.
- Authority, provenance, strength, target semantics, and lifecycle are separate.
- Omission creates no criterion; indifference is an explicit validated criterion.
- Only explicit/confirmed authority is storable; inference and search have no
  criterion write path.
- Every authoritative child and provenance reference is task-scoped; there is no
  global current task. A message source is also tied to the exact input that
  created that message.
- Revision history is row metadata around a current counter, not event replay.
- A lineage successor cannot drift to a different concept; forward temporal
  ordering and cycle rejection are explicit V0-04 transaction invariants.
- Fingerprint versions freeze structural canonicalisation without case-folding or
  otherwise rewriting user content.
- Categorical direction does not determine strength: both hard exclusions and
  soft negative preferences are representable.
- The shelving acceptance map contains only the stated width and depth.
- Required custom PostgreSQL DDL stays in the committed Drizzle migration history
  and is verified from the final database shape.
- Ordinary checks remain credential-free; only the explicit PostgreSQL suite
  requires a disposable local/CI database.
- Persistence modules are feature-specific and transaction-aware, not generic
  repository ceremony.
- V0-04 transitions, undo, and projection remain deferred.
- All three golden cases fit the same records and value grammar. The accepted
  candidate-comparison deferment keeps the one unavailable ownership guarantee
  explicit rather than faking it.
