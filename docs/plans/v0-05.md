# V0-05 — AI interpretation and context acquisition

## Status and objective

This is the planning-only execution brief for the first Gate 3 slice. It is
based on merged `main` at
`cbb3314a4dcb04ef6ff8b351fa7823ffdc0bf753`. Implementation is not authorised
until this plan is independently reviewed and accepted.

V0-05 must answer one measurable question:

> Given one persisted shopper input and the exact current authoritative task
> state, can a model propose a safe structured patch that captures only what
> the shopper expressed, preserve uncertainty, recognise explicit changes of
> mind, and help choose whether one worthwhile question is needed before
> productive search?

The model proposes. V0-04 remains the only authority that can validate and
apply shopping truth.

This slice deliberately optimises for learning rather than a universal intent
interpreter. It should finish with a small credential-gated local conversation
harness that can accept a message and show the resulting authoritative brief
plus ASK or SEARCH decision. It does not replace the fixture consumer UI or mix
live state with fixture product results.

## Planning correction: use two stages, not one compound answer

The initial implementation will keep these model contracts separate:

1. **Interpretation:** current input + authoritative snapshot → proposed state
   patch + bounded unresolved ambiguities.
2. **Context action:** original input + freshly reloaded authoritative concepts,
   active criteria, brief, revision, and capabilities → ASK, SEARCH, or
   capability-gated SHOW/REFINE.

The patch is applied, or safely rejected, before context-action selection. The
second stage never reasons against an unvalidated proposed state. A later
experiment may compare a combined provider call for latency, but its sections
would still require independent validation and the action decision would need
revalidation after patch application. V0-05 will not begin with that
optimisation.

## Exact boundary

### In V0-05

- Strict versioned provider-wire, interpretation, and context-action contracts
  with deterministic lowering into existing application/domain contracts.
- One OpenAI Responses API adapter behind narrow application interfaces.
- Configurable model, reasoning effort, prompt version, schema version, timeout,
  and output budget.
- Initial experiment using GPT-5.6 Terra at low reasoning, inherited from the
  approved V0 baseline; it is not a permanent model choice.
- Natural `message`, stored `question_answer`, and direct brief-action input
  content resolved from the existing task-scoped `TaskInput` boundary.
- Backward-compatible question-answer V2 for open text and single select, with
  snapshot-bound single-use ASK semantics and typed stale rejection.
- Exact current task market, concepts, active criteria, criterion IDs, and
  current revision supplied as the state snapshot.
- Proposed V0-04 patch operations only; no second mutation grammar.
- Bounded non-authoritative ambiguity records for diagnostics and evals only.
- Deterministic orchestration from persisted input through proposal validation,
  V0-04 application, state reload, and context action.
- One bounded stale reinterpretation against the newest authoritative snapshot.
- Duplicate-input convergence onto the already committed V0-04 result.
- Minimal persisted context-attempt diagnostics and an immutable selected-action
  artifact, without chain-of-thought or event sourcing.
- Refusal, incomplete, malformed, timeout, transport error, invalid patch,
  stale race, and retry behaviour that never partially mutates state.
- Deterministic contract/coordinator tests plus dated live-model eval reports.
- Cap, shelving, headphones, exact lookup, change-of-mind, ambiguity, and
  adversarial boundary cases.
- A local developer harness proving a real message can reach authoritative
  brief + context action without exposing a paid public endpoint.

### Not in V0-05

- Search hypotheses, query generation, search providers, retrieval, candidates,
  products, observations, assessments, ranking, or comparative judgement.
- Candidate-referencing criteria before real task-scoped candidate identity.
- Product-result-aware SHOW/REFINE behaviour before candidate state exists.
- Consumer UI replacement, real result cards, or combining live briefs with
  fixture product claims.
- Model-created authority, provenance, IDs, task scope, lifecycle, timestamps,
  revisions, or application receipts.
- Automatic application of inferred but unconfirmed preferences.
- Confirmation questions that bind a model-inferred criterion proposal to
  `user_confirmed` authority; the first slice asks elicitation/clarification
  questions whose answers are new explicit shopper input.
- Category schemas, global concept ontology, synonym database, vector search,
  long-term memory, workspace/user preferences, or cross-task concept reuse.
- A generic prompt framework, agent framework, workflow engine, event store,
  model gateway, audit platform, or provider-agnostic abstraction designed for
  hypothetical future stages.
- Fine-tuning, prompt optimisation services, streaming UI, background jobs, or
  broad cost/latency infrastructure.
- Retrieval or judgement evaluation; V0-05 measures interpretation and context
  acquisition only.

## Existing authoritative foundation consumed

V0-05 composes with the merged V0-03/V0-04 contracts rather than replacing
them.

- `TaskInput` and `UserMessage` already preserve the exact source, client action
  identity, request fingerprint, and revision observed by the client.
- `CurrentShoppingState` contains the independently identified task, market,
  task-local concepts, and active criteria with provenance.
- `StatePatchProposalV1` already provides the only allowed mutation grammar:
  create concept, add criterion, replace target, relax, tighten, remove, mark
  indifferent, or no change.
- V0-04 owns server IDs, task scope, authority, provenance, canonical values,
  lifecycle, revision CAS, idempotency receipts, complete mutation deltas,
  rollback, undo, and deterministic brief projection.
- An older source input may support a freshly interpreted command at a newer
  expected revision. V0-04 validates temporal admissibility but never performs
  the reinterpretation itself.
- Comparison persistence remains unavailable until a real task-scoped
  `CandidateListing` exists.

The interpreter must use exact existing concept and active criterion IDs when
it means to reuse or change them. It may create a new task-local concept only
when the current state contains no concept with the same shopper-specific
meaning. No fuzzy database lookup is added in this slice.

## Interpretation contract

### Trusted request envelope

Trusted application code constructs the request. The model never chooses task
scope, source identity, or revision.

```ts
type InterpretShoppingInputRequestV1 = {
  schemaVersion: 1;
  taskId: ShoppingTaskId;
  sourceInputId: TaskInputId;
  interpretedRevision: bigint;
  market: MarketContext;
  source: ResolvedShoppingInputV1;
  concepts: readonly ConceptContextV1[];
  activeCriteria: readonly CriterionContextV1[];
};
```

`ResolvedShoppingInputV1` contains only exact server-resolved content:

- message body for a `message` input;
- the stored selected question plus either server-resolved option meaning or
  exact open text for `question_answer`;
- exact submitted control text for `direct_brief_action`.

The model sees stable concept and criterion IDs because patch operations need
selectors. It does not see database rows, application receipts, hidden model
traces, search data, or a replayed transcript.

### JSON-safe provider input projection

The internal request type is not serialized directly: JavaScript `bigint` is
not JSON-safe and future internal records may contain dates or branded runtime
types. A pure, strictly validated provider-input projection converts only
transport representation:

- task and source IDs remain canonical strings;
- revisions become canonical non-negative base-10 strings;
- dates, if ever required by this slice, become UTC ISO-8601 strings;
- market, resolved source, concepts, and active criteria become bounded plain
  JSON objects with the same semantic values;
- no receipt, trace, database metadata, undefined value, or hidden transcript
  is included.

Projection cannot abbreviate or summarize semantic content. Configure a bounded
input budget before the provider call; if the complete resolved source and
authoritative concepts/criteria cannot fit, return typed `input_too_large`,
record a bounded failure attempt, and apply nothing. Never silently truncate the
shopper input, drop active criteria, or send a state snapshot different from the
one named by the revision.

The context-action stage uses the same JSON-safe projection rules for its
resolved source, current revision, concepts, active criteria, brief, and
capabilities.

### Provider wire output and lowering

The OpenAI schema is a transport schema, not `StatePatchProposalV1` exposed
directly. Current strict Structured Outputs require an object root rather than a
root `anyOf`, require every field, and require `additionalProperties: false` on
objects. V0-05 therefore uses a provider-compatible root object with required
discriminators, required arrays, and required nullable transport fields where a
domain branch would otherwise omit a property.

Conceptually:

```ts
type InterpretationProviderWireV1 = {
  providerSchemaVersion: 1;
  outcome: "change" | "no_change";
  operations: readonly ProviderPatchOperationWireV1[];
  ambiguities: readonly ProviderAmbiguityWireV1[];
};
```

Nested operation variants may use provider-supported `anyOf` only when every
branch is itself a valid strict object. The provider schema must not depend on a
top-level Zod discriminated union or on JSON Schema features unsupported by the
selected model/API. Provider-only nullability and wrappers represent absence or
branch shape; they never imply a semantic default.

The first wire schema deliberately differs from the current raw semantic-value
Zod where provider constraints require it:

- qualitative text and qualitative ordinal are separate closed wire variants,
  then lower to the existing qualitative domain value;
- measurement-range lower and upper are both required nullable bounds, and
  lowering requires at least one non-null bound;
- every provider object is strict and every property is required;
- comparison semantic values are absent from the V0-05 provider enum because
  real task-scoped candidate identity does not exist yet.

The boundary is exact:

```text
provider response
→ strict provider-wire validation
→ deterministic lowering
→ InterpretationProposalV1 / StatePatchProposalV1 validation
→ V0-04 application validation
```

Lowering is total over validated wire input and may only:

- select the domain branch identified by the wire discriminator;
- remove provider-only null wrappers;
- map closed provider operation tags to the identical V0-04 operation;
- reject incoherent branch combinations, such as `no_change` with operations.

It may not invent defaults, repair an operation, reinterpret text, alter
strength/target/operator/value, substitute IDs, or turn an invalid change into
`no_change`. Any lowering failure applies nothing.

### Application proposal

```ts
type InterpretationProposalV1 = {
  schemaVersion: 1;
  patch: StatePatchProposalV1;
  ambiguities: readonly InterpretationAmbiguityV1[]; // 0..4
};

type InterpretationAmbiguityV1 = {
  kind:
    | "unclear_reference"
    | "unclear_strength"
    | "unclear_value"
    | "possible_conflict";
  summary: string;                  // bounded diagnostic, not user truth
  existingConceptId: ConceptDefinitionId | null;
  affectedCriterionIds: readonly CriterionId[];
};
```

Ambiguities have no write capability. They exist to explain why the model
abstained on part of the message and to support diagnostics/evaluation. They are
not an input to context-action selection and are not required for crash
recovery. They contain no confidence number, hidden reasoning, guessed value,
or free-form operation.

A proposal may contain a change patch for clear explicit content and still
record a separate unresolved ambiguity. The ambiguous portion must not appear
in the patch. This does not relax the architecture rule against applying an
ambiguous output: every proposed operation must itself have one exact meaning,
or the entire patch is rejected. If nothing can be applied safely, the patch is
`no_change`.

### Interpretation rules

- Extract only explicit shopper truth or the explicit meaning of a stored
  answer.
- Unknown stays absent. Common category attributes are never pre-created.
- Reuse an exact existing concept ID when meaning is unchanged.
- Change current truth through exact active criterion IDs; never add a
  conflicting parallel criterion to avoid expressing supersession/removal.
- Preserve strength, target semantics, categorical direction, money mode,
  units, and indifference as separate dimensions.
- “Around” is not a ceiling. “Prefer” is not eligibility. “Open on brand” is
  indifference, not a list of acceptable brands.
- Search language, examples, brands mentioned as product history, and likely
  commercial synonyms do not automatically become criteria.
- A model inference may be recorded only as ambiguity/context for a possible
  question. It cannot enter the patch until the shopper explicitly answers or
  confirms it.
- If the shopper clearly changes their mind, propose the exact replacement,
  relaxation/tightening, removal, or remove-plus-add operations required by the
  current state.
- If the input is an exact product lookup or navigation instruction and states
  no durable decision criterion, propose `no_change`; context-action selection
  may still choose SEARCH.
- Candidate-relative language is unresolved in V0-05 because candidate identity
  does not yet exist. It must not fabricate a candidate ID or persist a textual
  stand-in.

### Conservative strength mapping

Strength is labelled semantic meaning, not sentiment scoring. Freeze the first
mapping in prompt examples and golden fixtures:

- `preference`: an ordinary explicitly desired property or flexible target.
  Phrases such as “I need a …” or “I'm looking for …” establish the shopping
  request but do not automatically make every following attribute hard.
- `strong_preference`: the shopper gives meaningful emphasis or priority, such
  as “really matters,” “matters more,” “I hate strong clamping,” or a clearly
  expressed aversion that stops short of eligibility/exclusion.
- `hard`: the shopper clearly states eligibility, exclusion, or a required
  bound, such as “must,” “no more than 60 cm,” “no white,” “only,” or “I won't
  consider …”.
- explicit indifference has null strength, as the existing domain requires.

When wording supports two strengths, choose the weaker one or abstain/ask. The
model must not infer hard from product-category convention, imperative tone, or
the word “need” alone. Lowering cannot strengthen the provider value.

## Proposed state versus authoritative state

The proposal is untrusted structured output, not pending truth.

1. Strictly validate the provider response and local schema.
2. Wrap the patch in a server-owned V0-04 command using the exact task, newest
   interpreted revision, and trusted authority source plan.
3. Submit it to `applyStatePatch` without repairing invalid operations.
4. Only the returned application and rebuilt brief are authoritative.
5. Reload current state before context-action selection.
6. Persist bounded diagnostic status separately from criteria.

The application never displays a proposed brief as though it were applied.
Malformed, refused, incomplete, invalid, or stale output applies no partial
patch.

For initial message and elicitation-answer flows, the resulting authority is
`user_explicit`: the shopper supplied the content being represented. The model
does not choose `user_confirmed`. A confirmation flow would need the application
to bind one exact non-authoritative proposed patch, its origin input, and
affirmative/negative answer semantics before constructing V0-04's trusted
`user_confirmed` source plan. That is deliberately deferred rather than
pretended through a loose question label.

## Context-action contract

The action selector runs after interpretation/application settles and consumes
the newly authoritative snapshot.

```ts
type SelectContextActionRequestV1 = {
  schemaVersion: 1;
  taskId: ShoppingTaskId;
  sourceInputId: TaskInputId;
  currentRevision: bigint;
  source: ResolvedShoppingInputV1;
  concepts: readonly ConceptContextV1[];
  activeCriteria: readonly CriterionContextV1[];
  brief: ShoppingBriefV1;
  capabilities: {
    supportsSearchAction: boolean;
    hasCurrentCandidates: boolean;
  };
};

type ContextActionProposalV1 =
  | {
      schemaVersion: 1;
      action: "ask";
      question: QuestionProposalV1;
    }
  | {
      schemaVersion: 1;
      action: "search";
      rationale: ContextActionRationaleV1;
    }
  | {
      schemaVersion: 1;
      action: "show_refine";
      rationale: ContextActionRationaleV1;
};
```

The deterministic brief is included because the action must align with what the
shopper can inspect, but it is not sufficient context by itself. Active
criteria are also supplied because the visible brief deliberately omits
indifference and other non-display state that must still prevent redundant or
contradictory questions. The selector receives no historical transcript and no
stage-one ambiguity proposal or diagnostic trace. It must be reproducible from
the resolved input and authoritative state after a crash/retry.

Context action also has a provider-compatible object root rather than exposing
the domain union directly:

```ts
type ContextActionProviderWireV1 = {
  providerSchemaVersion: 1;
  action: "ask" | "search" | "show_refine";
  question: ProviderQuestionWireV1 | null;
  rationale: ProviderActionRationaleWireV1 | null;
};
```

Every root field is required. Deterministic lowering rejects ASK without one
valid question, rejects a question on non-ASK branches, rejects missing branch
rationale, and then validates the closed `ContextActionProposalV1` domain union.
Provider nulls express branch absence only; lowering does not manufacture
question text or rationale.

`QuestionProposalV1` contains one bounded shopper-facing prompt, either
open-text response or 2–4 exact single-select options, qualitative expected
impact (`retrieval`, `eligibility`, or `judgement`), a bounded “why now”
rationale, and `canSearchWithoutAnswer`. It contains no numeric question value,
confidence, ranking score, or lifetime question count.

The provider returns visible option labels only. Trusted persistence assigns
server option IDs after selection; the model cannot choose IDs or attach hidden
criterion/patch payloads to an option.

V0-05 questions elicit or clarify shopper input; they do not present a
model-inferred criterion as a fact awaiting a yes/no rubber stamp. Their answers
therefore enter through a new `question_answer` input and are interpreted as
explicit content. Exact inferred-proposal confirmation remains a separate
authority path, not an overloaded option label.

Deterministic validation enforces:

- exactly one question when action is ASK and none otherwise;
- no duplicate/empty options and no option that silently asserts user truth;
- ASK must identify a plausible impact, not merely an unknown field;
- SEARCH requires `supportsSearchAction`;
- SHOW/REFINE requires `hasCurrentCandidates`;
- V0-05 sets `supportsSearchAction: true` because SEARCH is an allowed policy
  result returned to the caller; it does not execute retrieval in this slice;
- V0-05 supplies `hasCurrentCandidates: false`, so live SHOW/REFINE is not
  emitted until real candidate state exists;
- “Show me options now” should prefer SEARCH whenever a responsible exploratory
  search is possible.

Action rationale is diagnostic and evaluable. It is not chain-of-thought and
does not enter authoritative criteria.

## Backward-compatible question-answer V2

The existing TaskInput V1 `question_answer` requires `questionId`, `optionId`,
and `answerText`; inventing an option ID for open text or accepting client text
as the meaning of a selected option would corrupt provenance. Keep all V1 rows
and retry parsing valid, and add a versioned V2 question-answer request/payload
with two exact modes:

```ts
type QuestionAnswerInputV2 = {
  inputSchemaVersion: 2;
  expectedRevision: bigint;
  kind: "question_answer";
  questionId: ContextActionId;
  answer:
    | { mode: "open_text"; text: string }
    | { mode: "single_select"; optionId: ContextQuestionOptionId };
};
```

- Open text has no option ID and uses the bounded shopper-supplied text.
- Single select has no client-supplied semantic text. The server resolves the
  exact stored visible option label in the context of the stored prompt; client
  display text is ignored or rejected rather than treated as authority. The
  option carries no hidden criterion value or patch meaning the shopper could
  not inspect.
- V1 remains readable and idempotently retryable. New V0-05 ASK answers use V2;
  there is no in-place reinterpretation of persisted V1 JSON.
- Preserve the V1 fingerprint canonicalizer exactly for historical retries and
  add fingerprint V2 for the V2 envelope. It includes input schema version,
  response mode, exact question ID, and either open text or option ID. A stored
  fingerprint version always reproduces its original canonical envelope.

Question-answer recording uses a narrow immutable `context_action_answers`
binding with same-task composite foreign keys, unique `(task, action)` and
unique `(task, answer input)` identities. It validates, in one transaction:

1. the referenced action exists in the same task and is ASK;
2. the answer mode matches the stored question response mode;
3. a selected option belongs to that exact question;
4. the request `expectedRevision`, question snapshot revision, and locked task
   current revision are equal;
5. no different answer input is already bound.

An exact duplicate client action/fingerprint returns the existing answer/input
and later V0-04 receipt even after its successful patch advanced the task. That
idempotent winner probe occurs before stale/single-use rejection. A different
second answer fails with typed already-answered behaviour. If the task advanced
after question selection, the first answer attempt fails with typed
`StaleContextQuestionError` before any model call or semantic mutation.

This strict snapshot rule applies to ASK answers because their meaning is bound
to one selected question/state. Ordinary natural messages retain the normal
bounded stale reinterpretation path.

## Persisted action and question identity

A selected action needs its own recoverable artifact in addition to the patch
receipt. A process can commit the V0-04 patch and fail before choosing ASK or
SEARCH, so patch idempotency alone is not completion of V0-05. V0-05 adds one immutable,
task-scoped `context_actions` artifact uniquely bound to the validated V0-04
state-change application rather than treating diagnostic traces as workflow
state.

It records:

- server-owned action ID and owning task;
- exact state-change application receipt and authoritative revision used for
  selection;
- selected ASK, SEARCH, or capability-valid SHOW/REFINE action;
- for ASK only, prompt schema version, exact prompt, response mode, typed
  server-owned option IDs plus exact visible labels, qualitative impact,
  why-now rationale, and
  `canSearchWithoutAnswer`;
- selected model/prompt configuration identifiers and timestamp.

The action is an application artifact, not shopper truth. When its action is
ASK, its server ID is also the stable question identity. A `question_answer`
input must resolve that exact ASK artifact in the same task. The server supplies
the stored prompt plus either the server-resolved selected visible label or the
exact open answer text to interpretation. Cross-task, missing, non-ASK, or
altered question identity fails before a model call.

The unique action artifact is also the idempotent result of stage two. If two
handlers select different valid actions concurrently, the first committed
artifact wins and both return it; the losing proposal is diagnostic evidence
only. A retry that finds a V0-04 receipt but no action artifact resumes from the
fail-closed-validated receipt, reloads the latest authoritative task state, and
completes action selection. It does not reinterpret or reapply the patch.

The database uses a same-task composite foreign key to the receipt and a unique
receipt identity, so no action can exist without one completed authoritative
stage-one result, including `no_change`. Source input is derived from that
receipt. If retained as a query column, it must be bound to the same receipt by
one composite constraint rather than trusted through independent foreign keys.

Action persistence uses its own narrow revision check: the task revision must
still equal the snapshot revision used by the selector when the artifact is
inserted. If it advanced, discard the action proposal, reload, and allow one
new action selection. A second action-stage race returns a retryable no-action
result; it never persists a stale question. This is a bounded CAS around one
artifact, not a workflow engine.

V0-05 does not build a generic questionnaire, mutable workflow state, or global
question catalogue. The immutable one-answer binding exists solely to prove
single use, task scope, exact option ownership, and idempotent retry; it is not a
broad status machine.

## Minimal diagnostic trace

Add one V0-05-specific `context_acquisition_attempts` record, not a generic
model/event framework. Each stage attempt records only bounded structured
artifacts needed to reproduce evals and failures:

- task, source input, snapshot revision, stage, and attempt ordinal;
- prompt/schema/config version and actual provider/model identifiers;
- status: completed, refused, incomplete, malformed, timed_out,
  provider_failed, invalid_patch, stale, or superseded_by_winner;
- validated interpretation proposal or context-action proposal in separate
  typed nullable columns/contracts;
- duration, provider request ID when available, token usage, and sanitised error
  code;
- resulting state application ID or selected context-action ID when
  successful.

The original shopper input remains canonical in `TaskInput`/`UserMessage` and
is not copied wholesale as a second transcript. A validated structured proposal
may naturally repeat bounded user-derived labels, definitions, values, question
copy, or summaries needed to diagnose its semantics; the plan does not pretend
otherwise. No raw chain-of-thought, full prompt transcript, full provider
envelope, secret, or raw stack dump is stored. Trace rows never rebuild current
truth and are not replayed as events.

If implementation shows that this diagnostic record cannot remain small and
stage-specific, stop for review rather than inventing a generic observability
platform.

## Orchestration, idempotency, and stale reinterpretation

### Normal flow

1. Idempotently record or load the exact `TaskInput`. Natural messages use the
   existing path. For question-answer V2, resolve/lock the ASK artifact, validate
   same-task response mode, option ownership, snapshot revision and single use,
   then record/load the TaskInput and immutable answer binding atomically before
   any model call. An exact duplicate winner returns before stale rejection.
2. If V0-04 already has an application receipt for the causal input, do not
   reinterpret or reapply it. If its context-action artifact also exists,
   return the two committed results. Otherwise resume at step 8 from the
   receipt's fail-closed-validated resulting state.
3. Load current authoritative state at revision R.
4. Resolve any stored question context and build the interpretation request.
5. Call the interpretation adapter outside a database transaction.
6. Strictly validate the response; on failure record a bounded diagnostic and
   preserve state.
7. Apply the proposed patch through V0-04 with `expectedRevision = R`.
8. Reload authoritative state and run context-action selection.
9. Validate and atomically select the unique context-action artifact, including
   its question payload when action is ASK, only if the task revision still
   matches the selector snapshot. A concurrent same-input winner is returned
   instead of overwritten; one unrelated revision race may rerun selection
   against the latest state.
10. Return the V0-04 application/delta, current brief, action, and recoverable
    failure state to the caller.

### Stale output

If V0-04 rejects the proposal because current state advanced after the snapshot:

1. Discard the stale proposal completely.
2. Reload current authoritative state.
3. Reinterpret the original persisted source input against that state.
4. Allow one semantic reinterpretation only (two interpretation attempts total).
5. If state advances again, return a typed retryable stale result with no new
   semantic mutation or question.

Never rebase selectors, patch IDs, or semantic values mechanically. Never feed
the stale model proposal back as shopper truth.

### Duplicate orchestration

No database transaction remains open across a model call. Concurrent handlers
may therefore both interpret the same idempotent source input. V0-04 remains the
write mutex and application authority:

- the first valid application wins;
- a later identical application returns the same receipt;
- if model nondeterminism yields a different proposal, the coordinator loads
  and returns the already committed winner rather than surfacing a second truth;
- the divergent proposal is recorded only as `superseded_by_winner` diagnostic
  evidence for model evaluation.

Patch completion and action completion are separate idempotent checkpoints. A
retry after patch commit but before action commit resumes only the action stage.
The unique context-action artifact similarly converges concurrent action
selection onto one returned result. Diagnostic attempt rows are never used as
the source of either result.

This requires one narrow fail-closed read boundary for validated
application-by-causal-input. It reuses the historical receipt/materialized-state
validation already required by V0-04; it never shallow-maps a receipt. The
coordinator uses it for crash recovery and, when `applyStatePatch` detects a
different same-input proposal fingerprint, to return the already committed
winner while recording the losing proposal as diagnostic evidence. Do not
weaken V0-04's fingerprint conflict. No input lock spans an external call, and
no lease system or workflow queue is added.

Provider transport retry is separate from semantic stale reinterpretation. One
retry at the same snapshot is allowed only for explicitly retryable transport or
rate-limit failure and must respect the same overall deadline. Refusal,
incomplete output, schema failure, and deterministic patch rejection are not
blindly retried with the same prompt.

A rate-limit retry honours the provider's bounded `Retry-After` value only when
the delay and second call can remain inside that deadline. Quota exhaustion is
terminal, and a delay longer than the deadline fails closed without spending a
second request.

## OpenAI adapter and structured-output failure handling

The adapter uses the official server-side JavaScript SDK and Responses API with
strict JSON-schema Structured Outputs. Current official OpenAI documentation
states that Structured Outputs adhere to the supplied schema, while refusals
are separate output content and incomplete responses remain an explicit status:
<https://developers.openai.com/api/docs/guides/structured-outputs>.

Implementation must still branch explicitly on:

- completed structured output;
- refusal content;
- `incomplete` response and its reason;
- failed/cancelled response status where returned;
- zero or multiple relevant assistant message payload/refusal paths after
  scanning `response.output` and ignoring permitted non-message items such as
  reasoning metadata;
- SDK/transport error, timeout, rate limit, and server error;
- local strict-schema failure despite provider guarantees;
- local semantic/V0-04 patch rejection.

The parser does not assume `response.output.length === 1`. For a completed
response it locates assistant `message` items, inspects their typed content,
and requires exactly one relevant parsed structured payload or one refusal
path. Mixed refusal/payload, duplicate payload, unsupported message content, or
no relevant content fails closed. Only one completed, non-refusal, strictly
validated wire object reaches lowering and then the coordinator. Output is never
repaired with regex, tolerant JSON parsing, or a second “fix this JSON” model
call.

Use `store: false` for these one-shot task-context calls unless a reviewed
provider-data requirement demonstrates otherwise. Do not use conversation
state, `previous_response_id`, web search, file search, tools, or the model's
memory. Send only the current source input and bounded authoritative snapshot.

The adapter remains configurable. The implementation/eval report must record
the actual model snapshot/alias, reasoning effort, latency, tokens, refusal or
incomplete status, and prompt/schema versions. Terra low is the starting
experiment, not an invariant.

## Prompt design discipline

Use two short versioned prompts, one for each contract. Prompts state protected
semantic rules once and describe exact input/output responsibilities. They do
not contain category-specific taxonomies or duplicate the entire architecture
document.

Interpretation examples should teach distinctions that are hard to infer from
the schema alone:

- around versus maximum versus conditional stretch;
- categorical include/prefer/exclude;
- unmentioned versus indifferent;
- existing-concept reuse and exact criterion replacement;
- product-history/search language versus authoritative preference;
- explicit change of mind;
- partial interpretation with ambiguity held outside the patch.

Question examples should teach interruption quality, exact lookup with zero
questions, “show now,” one useful fit question, and low-value unknowns that do
not justify ASK.

Few-shot examples are hypotheses. Start with the smallest set that passes the
golden cases, record prompt versions, and change prompts only with an assigned
failure. Do not optimise one giant prompt against an aggregate vibe.

## Evaluation method

### Two complementary suites

1. **Deterministic contract/coordinator tests** use fake adapters and real V0-04
   persistence. They gate CI and prove state safety, retries, idempotency,
   provenance, stale handling, and failure preservation.
2. **Live model evals** use versioned labelled cases and the real adapter. They
   are credential-gated, non-CI, dated, and write a sanitised JSON plus concise
   Markdown report. Human labels are authoritative; an LLM grader is never the
   sole judge.

The live command must not mutate shared developer tasks. It uses disposable
test tasks/database scope and fails clearly when credentials are absent.

Before the release run, freeze each protected case's exact semantic expectations
and acceptable action set. Execute every protected core case three times at the
release model/configuration. The report includes run/case denominators,
per-measure outcomes, and observed variance. Acceptance requires zero invented
criteria and zero other protected-invariant violations across all release runs;
one lucky completion is not evidence. Wording variation remains acceptable when
the labelled semantic/action contract passes.

### Layered measures

Report per-case outcomes rather than one flattering score:

- explicit criterion recall;
- fabricated criterion count and protected-invariant violations;
- exact strength/target/value/operator preservation;
- deterministic-lowering semantic identity for every supported operation/value
  wire branch;
- existing-concept reuse versus duplicate concept creation;
- change-of-mind/supersession correctness;
- unknown versus indifference correctness;
- safe abstention on ambiguous or candidate-relative content;
- ASK/SEARCH confusion matrix against human-acceptable actions;
- question usefulness and whether it asserts unsupported truth;
- exact-lookup and “show now” zero-question behaviour;
- invalid/refused/incomplete/timeout state-preservation rate;
- stale reinterpretation success and duplicate convergence;
- latency and input/output tokens by stage/configuration; estimated cost only
  when the dated report identifies the pricing source/version used for the
  calculation.

Protected semantic violations are hard failures even if other fields are
correct. Question wording may have multiple acceptable answers, so reviewers
label acceptable action/question properties rather than one exact sentence.

### Failure assignment

Assign each failure to the earliest responsible layer:

- input/question resolution;
- prompt/context construction;
- model interpretation;
- output contract;
- V0-04 state validation/application;
- stale/idempotency coordination;
- context-action policy;
- question persistence/presentation.

Do not “fix” state-engine rejection by weakening V0-04. Do not fix action-policy
failures by letting ambiguity mutate criteria.

## Required golden and adversarial cases

### Cap

- Initial message creates only lightweight `preference` and breathable
  `preference` qualitative truth.
- It does not add colour, budget, UV protection, retailer, or brand.
- “Old Nike race cap” is handled in context: Nike becomes a preference only
  when the shopper explicitly says it is preferred; `race cap`, `packable`, and
  `unstructured` remain absent from criteria unless explicitly wanted.
- “Too thick and substantial” plus “barely felt like anything” adds/updates
  minimal physical bulk as `strong_preference` without a cap schema.
- Explicit “Nike is preferred but I'm open” creates Nike `preference`, not
  `hard` eligibility.
- “I don't care about brand” replaces that brand preference with explicit
  indifference (null strength) and keeps brand out of the visible brief.
- Candidate-relative “number three” abstains safely in V0-05.

### Shelving

- Around £30 is `preference` with around/target semantics, not `hard` ceiling.
- “No more than 60 cm wide and 30 cm deep” creates hard maximum bounds; “No
  white” creates a hard categorical exclusion.
- Dark is `preference`; “I don't want anything visually bulky” is
  `strong_preference` for visual lightness, not a fabricated measurable bound.
- “I could go to £40 if it looks much better” replaces the prior budget with
  `preference` target-plus-conditional-stretch; it does not leave conflicting
  budget truth.
- No height, material, room style, or retailer criterion appears.

### Headphones

- Wireless `preference`, over-ear `preference`, around-£150 `preference`, clamp
  comfort `strong_preference`, ANC `strong_preference`, and brand indifference
  with null strength remain distinct.
- No colour, microphone, codec, battery, or ecosystem criteria appear.
- “Comfort with glasses matters more than strongest ANC” keeps comfort
  `strong_preference`, relaxes ANC to ordinary `preference`, changes only the
  explicitly affected priorities, and reuses existing concepts.

### Context action

- Exact model lookup normally chooses SEARCH with no question.
- A vague but searchable request may ASK one high-impact question or SEARCH if
  exploration is responsible; acceptable labels are explicit per fixture.
- Shelving fit may justify one dimensions question.
- Unknown colour/brand alone does not justify interruption.
- An indifferent concept is not re-asked merely because it is absent from the
  visible brief.
- “Show me options now” chooses SEARCH when possible.
- ASK never manufactures the answer it is requesting.
- SHOW/REFINE is rejected when candidate capability is false.

### Safety and resilience

- Malformed, extra-key, wrong-ID, cross-task, candidate-fabricating, comparison,
  and over-32-operation outputs apply nothing.
- A provider-wire matrix covers every supported operation and semantic-value
  family plus nullable/incoherent branches; lowering preserves IDs, local refs,
  strength, target semantics, operators, values, and units exactly or rejects.
- Refusal, incomplete output, timeout, and provider failure preserve the input
  and current state.
- A clear partial patch may apply while its separate ambiguity remains
  non-authoritative; an ambiguity never leaks into the brief.
- One stale race triggers reinterpretation against the latest snapshot; a
  second returns retryable failure with no partial state.
- Duplicate concurrent handling converges on one V0-04 receipt/result even when
  fake adapters produce divergent proposals.
- A retry after patch commit but before action commit resumes action selection
  without reinterpreting the input, and a task revision race cannot persist a
  stale question.
- A question answer cannot resolve a missing or cross-task stored question.
- Open-text answers require no option; single-select answers resolve exact
  server-stored option meaning and cannot be redefined by client text.
- A stale first answer or a different second answer fails before a model call;
  an exact duplicate retry returns the original winner.
- Provider/model text cannot assign server-owned authority, provenance, IDs,
  task ownership, lifecycle, or revision.

## Implementation sequence

Keep each step independently testable and keep the existing UI/browser suite
green.

1. **Contracts and fixtures.** Add strict provider-wire schemas, deterministic
   lowering, interpretation, ambiguity, context-action, question-answer V2,
   provider-result, and typed error contracts plus labelled golden inputs.
   Reuse V0-04 only after lowering; do not expose its root union to the provider.
   Prove schema generation through the actual OpenAI helper and semantic-identity
   lowering across every supported branch.
2. **Action, answer-binding, and diagnostic persistence.** Add the narrow
   task-scoped action, one-answer binding, and attempt records, generated
   migration/custom guards only where necessary, fail-closed mappers, and
   migration-from-empty tests. Prove an action can resume after a committed
   patch, concurrent selectors converge, open/select answers resolve exactly,
   and stale/double answers fail before model execution.
3. **Pure request builders.** Resolve exact input/question content and construct
   bounded model context from current state with snapshot tests proving no
   transcript/search/trace leakage.
4. **Provider adapter.** Add official SDK integration, configurable prompt/model
   settings, provider-compatible strict Structured Outputs, exact relevant
   message/refusal parsing, timeout/status handling, lowering, and a fake
   adapter. No tools or retrieval.
5. **Interpretation coordinator.** Validate proposal, call V0-04, converge
   duplicate winners, implement one stale reinterpretation, and preserve state
   on every failure.
6. **Context action and question selection.** Reload authoritative state, call
   the separate action contract, enforce capability rules, and persist exactly
   one immutable selected-action result, with a question payload only for ASK.
7. **Evaluation harness.** Add deterministic coordinator coverage and the
   credential-gated dated live report across golden/adversarial cases. Compare
   Terra low with at least one justified alternative or effort setting only
   after the baseline report exists.
8. **Local conversation proof.** Add a server-only local command/harness that
   creates or resumes a disposable/developer task, processes sequential inputs,
   and prints applied delta, authoritative brief, ASK/SEARCH action, latency, and
   recoverable failure. Before acceptance, run at least one same-task real-model
   journey through initial message → ASK → V2 open-text or single-select answer
   → authoritative patch → SEARCH, followed by one explicit change of mind. It
   must never expose secrets or become a public route.
9. **Review.** Inspect failure assignments, live examples, migrations, scope,
   dependency audit, and all repository gates. Stop before retrieval or
   consumer UI integration.

## Exit evidence

V0-05 is complete only when:

- cap, shelving, headphones, exact-lookup, and change-of-mind cases produce
  human-acceptable authoritative state without protected semantic leakage;
- model output cannot bypass V0-04 or mutate state on refusal, incomplete,
  malformed, invalid, timeout, or stale failure;
- unknown, indifference, preference, hard constraint, around, ceiling, and
  stretch remain observably distinct;
- the question policy asks at most one worthwhile question, permits zero, and
  does not turn generic unknowns into a questionnaire;
- duplicate and stale handling are proven against real persistence;
- the selected action is task-scoped and idempotent, and an ASK identity remains
  answerable after refresh;
- open-text and single-select V2 answers preserve exact server-owned question
  semantics, single use, stale rejection, and duplicate retry;
- a dated live report records actual model/config quality, latency, usage, and
  assigned failures;
- the local conversation harness can produce authoritative brief + ASK/SEARCH
  from a real model call and has completed the required same-task ASK/answer,
  SEARCH, and change-of-mind journey;
- existing quality, persistence, and browser gates remain green;
- no retrieval, product/candidate, assessment/judgement, fixture-UI replacement,
  workspace memory, or V0-06 work has begun.

## Deliberate open questions for implementation review

These are experiments, not reasons to design a larger architecture now:

- Does Terra low meet the semantic hard gates, or does interpretation require a
  different model/effort than context-action selection?
- Is two-stage latency acceptable once measured, and if not, can provider-call
  combination preserve independent validation and post-application action
  correctness?
- Which few-shot examples improve generalisation rather than overfit the three
  golden categories?
- Is the bounded context-attempt record sufficient for diagnosis without
  becoming a generic trace platform?
- Which question formats produce useful answers without steering shoppers into
  invented criteria?

Record answers through dated eval evidence. Do not turn an unmeasured hunch into
a permanent model, prompt, latency, or schema decision.

## Stop condition

The implementation task must end with a draft V0-05 PR and independent review.
Do not merge it automatically. Do not begin retrieval, search-provider work,
real candidate state, judgement, or consumer UI integration.
